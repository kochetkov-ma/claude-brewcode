# Best practices

- Use available Codex-native tools and project agents; parallelize independent bounded work when delegation is authorized. Claude tools such as `Task`, `Agent`, `Write`, and `Edit` are not Codex tool names.
- Prefer compact tables or code when they preserve meaning better than prose. Retain scope, negation, exact values, and paths.
- For an explicitly requested release, use the authoritative bump script and add `> Docs:` links to affected pages in `RELEASE-NOTES.md` through `$docs`. Follow the root release sequence; do not install or refresh plugins as a Codex runtime prerequisite.

## Claude product authoring only

These tokens belong to shipped Claude Code prompts, not Codex configuration or shell environment variables:

- `${CLAUDE_SKILL_DIR}` refers to a skill's own files; `${CLAUDE_PLUGIN_ROOT}` refers to plugin agents, hooks, and MCP assets. Write the bare literal token: prompt text substitution does not recognize `${VAR:-fallback}`. A brace modifier reaches the shell unchanged; an unset variable silently selects the fallback.
- `${CLAUDE_PLUGIN_ROOT}` substitution applies to plugin agent Markdown, not project-local `.claude/agents/*.md`; use repo-relative paths in local agents.
- Do not reintroduce removed `BC_PLUGIN_ROOT`, `BT_PLUGIN_ROOT`, `BD_PLUGIN_ROOT`, or `BU_PLUGIN_ROOT` injection.
- Assets with install-time `{PLUGIN_VERSION}`, `{GENERATED_BY}`, or `{LAST_UPDATED}` placeholders must not also be baked into `STAMPED_FILES`. Keep single braces; mixing the two stamp mechanisms causes baseline drift on each release.

### Shipped Claude skills and setup lifecycle

These contracts apply to Claude product artifacts, including generated Claude skill templates, not native `.codex/skills/`.

- Distributed skills: bare kebab-case `name` equals the directory name; never bake a plugin prefix into it. Frontmatter order: `name, description, user-invocable, disable-model-invocation, argument-hint, allowed-tools, model`. Require both `user-invocable: true` and explicit `disable-model-invocation: true`; `allowed-tools` is a bracket-list. Model auto-invocation is prohibited for distributed Claude skills.
- `argument-hint` starts with optional `[prompt]`, a free-form RU/EN prompt; retain existing modes/flags/targets afterward. Resolve mode and scope from prose. With 2+ modes, supply EN/RU keyword columns and `Mutates?`; strip flags, explicit mode wins, otherwise score distinct whole-word hits. Destructive tie → `AskUserQuestion`; read-only tie → `status`; two mutating modes → first keyword; no hits/empty input → documented default. At most one clarifying `AskUserQuestion`, max four questions, only when the answer changes what gets written.
- Before the first action, print `PLAN — <plugin>:<skill>` with these literal labels in order: `INPUT:`, `MODE:`, `SCOPE:`, `DO:`, `RESULT:`; read-only modes print it before reporting. Only pure reference/lookup skills with no modes and no writes listed in the canonical prompt contract AND registered in `validate-skill.sh` are exempt from the mode table and PLAN; they still accept `[prompt]`. The exhaustive current exemption is `.claude/skills/claude-plugin-guide`; do not infer others. Read the full [prompt contract](../../brewcode/skills/skills/references/prompt-contract.md) for routing and confirmation details.
- Use `-setup` only for installers of a mechanism used afterward; recurring tools keep bare names. Canonical modes, in order: `status | install | upgrade | enable | disable | uninstall | purge`; extras follow. Preserve each setup's documented default and executable resolution; verify both before changing them. Report conflicting sources rather than imposing a universal empty-input default. [Teams' parser](../../brewcode/skills/teams-setup/scripts/detect-mode.sh) and [docsync](../../brewdoc/skills/docsync-setup/SKILL.md) use installed → `status`, absent → `install`; [semble routing](../../brewcode/skills/semble-setup/references/intent-routing.md) always defaults to read-only `status`, never a bare machine-level install. Do not restore aliases `init, on, off, setup, remove, reset, create, update, cleanup`.
- Every setup requires reversible `enable`/`disable`: either a live config flag rechecked each invocation, or discovery-entry parking as `<name>.disabled` with byte-identical body and no deletion. Preserve each reader's semantics: docsync absent key means enabled (`c.enabled !== false`); agent-deadline/agent-return absent key means disabled (`enabled !== true`). Update `setup-status` Phase 1b probes in lockstep with setup lifecycle changes.
- Start from the closest well-built product exemplar and consult the tracked [skill-authoring reference](../../brewcode/agents/skill-creator.md). [Agent-return-setup](../../brewtools/skills/agent-return-setup/SKILL.md) is a structural frontmatter/PLAN/lifecycle exemplar; its default-mode descriptions conflict, so it is not a default-routing reference. Claude tools in those sources describe product contracts, not executable Codex instructions. Validate every affected Claude product skill directory with `bash brewcode/skills/skills/scripts/validate-skill.sh <affected-skill-directory>`; rerun after fixes. This validator does not target native Codex skills.
