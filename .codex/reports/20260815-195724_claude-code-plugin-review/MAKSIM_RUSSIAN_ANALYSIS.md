**Дата ревью:** 2026-08-15

## Главный вывод

Все три плагина работают на обычных сценариях, и ревью не обнаружило причины считать всю архитектуру неудачной. Переписывать плагины целиком не нужно.

При этом отсутствие заметных ежедневных проблем не означает, что слабых мест нет. Большая часть подтверждённых дефектов проявляется не на happy path, а при смене рабочей директории, параллельных сессиях, ошибке посередине установки или публикации, нескольких областях установки, грязном Git-дереве, необычном вводе, отключённых в новых моделях инструментах либо ответе внешнего сервиса формата «HTTP 200, но фактически ошибка». Именно поэтому существующие проверки могли проходить, а плагин мог выглядеть полностью исправным.

- Метрика **«144/145»** относится к одному сюиту `suite-integration`; реальный агрегат — **1789/1790 по 7 сюитам**, единственный провал — тот же SS09.
- **SS10** — **2** ошибки shellcheck (`SC1073`, `SC1072`), а не 4: форматтер по умолчанию печатает две находки четырьмя строками.
- Ссылка **F12** указывает на скрипт на Python (`skills.md:1005-1012`); верная строка — **`skills.md:1028`**.
- **«v3.4.70 — несуществующая версия Claude Code»** неверно: это git-тег brewcode с реальным происхождением (`RELEASE-NOTES.md:2341,2348`, эмпирическая проверка в headless `claude -p`). Нужна не удаление, а уточнение пространства имён («brewcode v3.4.70») и переподтверждение на 2.1.233.
- Лимит **200 сабагентов действительно снят** в 2.1.224 (`CHANGELOG.md:191`) — противоречия между документацией и CHANGELOG нет.
- Заявление **BCOP02** про мутацию установленного кэша **ложно**: в `brewcode/skills/agents/` ноль обращений к `CLAUDE_PLUGIN_ROOT`/`plugins/cache`. Реальный, меньший дефект: в чужом репозитории `brewcode/agents/` не существует, поэтому shipped-агенты не видны, а выбор scope «Plugin» создаёт мусорный `<cwd>/brewcode/agents/<name>.md`.
- Побочно: `brewtools/hooks/agent-return-guard.mjs` не существует; счёт `${CLAUDE_PROJECT_DIR:-…}` в brewdoc — 12 в трёх скилах, а не 11 в двух.

### Разрешённые противоречия

- **`${CLAUDE_PLUGIN_DATA}`** — официальный постоянный записываемый каталог (`plugins-reference:665,705,721`, туда пишет собственный скил Anthropic). Запись через `Write`/`Edit` даёт **ЗАПРОС подтверждения**, а не блокировку: в `default`/`acceptEdits`/`plan` — промпт, под `bypassPermissions` — автоодобрение, в headless (`-p`) без bypass — **падение** («no prompt available in headless mode»). Формулировка `hook-creator.md:300` («blocked in ALL modes») ложна и подлежит замене. Для автоматической записи по-прежнему годится только Bash/хук-подпроцесс либо `${CLAUDE_PROJECT_DIR}/.claude/<subdir>/`.
- **Ввод секрета в обход видимости модели во время работы** — такого канала **НЕТ**. `AskUserQuestion` не имеет маскируемого поля (в схеме только `question`/`header`/`options`), у скила нет собственного примитива ввода. `userConfig` с `"sensitive": true` существует, но работает только на этапе включения плагина и намеренно не подставляется в текст скила или агента. Единственное здравое решение: пользователь заранее задаёт `export VAR` или файл с правами 600, а скил читает `$VAR` в Bash без вывода на экран.

## Как отфильтрованы выдумки и overengineering

Для каждой оставленной находки требовалось независимое подтверждение минимум двумя агентами. Проверялись конкретные строки, входное состояние, наблюдаемый результат, радиус воздействия и минимальное направление исправления.

Правило было намеренно асимметричным: если второй агент отвергал предпосылку, не мог воспроизвести результат или подтверждал только более узкий сценарий, широкая формулировка удалялась либо сужалась. В отчёты не переносились «на всякий случай», общие best-practice пожелания и предложения построить новую абстракцию без конкретной неисправности.

В частности, исключены или сужены следующие заметные гипотезы:

- не подтверждён предполагаемый конфликт между deadline cleanup и agent-return;
- `shell: bash` не объявлен несовместимым с обычными prose Bash-блоками;
- Semble 0.5.5 зафиксирован как update intelligence, но сам факт наличия новой версии не назван дефектом;
- npm-дефект BREWCODE не выдан за поломку загрузки Claude Code plugin;
- SSH option injection оставлен только для воспроизведённого невалидированного port-вектора;
- agent-return ограничен коллизией каталога отчёта, без ложного утверждения о коллизии retry-state;
- portable Python/Python-pip проблема BREWDOC не названа активной неисправностью на текущем Mac;
- утверждения о гарантированной потере смысла при любом прошедшем text-optimization gate удалены.

## Что действительно стоит делать первым

### Волна 0 — остановить генерацию новых устаревших артефактов

Сначала нужно синхронно обновить три reference-файла и три creator-агента под зафиксированный контракт 2.1.233. Обновление только reference без creator или только creator без reference оставит два противоречащих друг другу источника.

Минимальный объём:

1. Исправить таблицы frontmatter, tool availability, scope/precedence, foreground/background/fork, nested agents и managed agents в `agent-creator`.
2. Переписать hook inventory и точные event-specific input/output contracts в `hook-creator`, включая exit-code semantics, matchers, exec form, plugin-scoped MCP и lifecycle/reload boundaries.
3. Исправить `allowed-tools`, удалить выдуманные обязательные `cli`/`version`, обновить Agent/Skill orchestration, hook events, scope, path substitutions и paired evaluation в `skill-creator`.
4. Добавить небольшие contract fixtures против замороженной версии. Не нужен новый framework: достаточно валидировать поддерживаемые поля, события и несколько решающих runtime-сценариев.

### Волна 1 — реальные границы безопасности и потери данных

После creator-слоя приоритет следует отдать дефектам, где ошибка может раскрыть секрет, выполнить неожиданный shell-код, удалить пользовательский файл, разрушить рабочую регистрацию или выпустить не тот код:

- BREWTOOLS: четыре обхода hard-mode guard; model-visible provider/registry secrets; запись найденных секретов обратно в отчёт; release flow, который захватывает лишние dirty files/tags; GitHub workflow interpolation; SSH lockout/host trust; перезапись malformed settings.
- BREWDOC: shell-source interpolation в publish и архивирование всего каталога, включая `.env`, `.git`, dependencies и caches.
- BREWCODE: Semble reindex, способный удалить рабочий index и сообщить ready; отсутствие rollback при MCP repair; удаление ранее существовавших user agents; traversal в team roster/rule prefix; уничтожение чужого `.claude/plans/LATEST.md`; перезапись user-authored `intent-guard`.

Здесь нужны локальные исправления на конкретных границах: structured argv/stdin вместо генерации shell source, ownership marker/hash, canonical containment, staged replacement, rollback и точный scope. Общий security framework не требуется.

### Волна 2 — корень проекта, конкуренция и единое состояние

Следующий общий кластер — смешение `cwd` с project root. Он подтверждён независимо в BREWCODE, BREWTOOLS и BREWDOC. После `/cd` или работы из nested package плагины могут читать либо писать другой `.claude`, терять конфигурацию и показывать ложный статус.

Нужно один раз для каждого runtime surface определить авторитетный project root и использовать текущий cwd только для относительных пользовательских путей. Одновременно следует исправить:

- concurrent read/modify/write settings без lock/atomic merge;
- общие docsync state-файлы между сессиями;
- одинаковые каталоги agent-return для одинакового agent type в одну секунду;
- параллельную выдачу task-board IDs;
- status/readiness, который вычисляется разными предикатами в разных фазах;
- version/content-version сравнения, создающие постоянный false-stale loop.

### Волна 3 — точность инструментов и переносимость

Последними можно исправлять подтверждённые, но менее срочные расхождения: inventory boolean defaults, convention file counts, npm-only packaging, Semble test expectation, ShellCheck directive, PDF style/result reporting, Python interpreter pairing, PowerShell hook command, macOS отсутствие GNU `timeout`, выбранный plugin update scope и переносимые SSH/deploy шаблоны.

Они не должны блокировать первые волны, но их стоит закрыть, потому что ложный status или зелёная проверка постепенно уничтожают доверие к инструменту.

## Почему существующие тесты этого не поймали

Механические и happy-path проверки в основном проходят:

- strict plugin validation проходит для всех трёх plugin roots;
- проверенные JavaScript, Bash, JSON и Python файлы синтаксически валидны;
- BREWTOOLS hook/setup suites дали сотни успешных тестов;
- PDF был реально сгенерирован;
- Semble aggregate suite дала 1789/1790 по 7 сюитам (144/145 — это только `suite-integration`), с одной подтверждённой устаревшей expectation.

Эти результаты полезны, но они отвечают на вопросы «файл парсится?» и «обычный сценарий работает?». Подтверждённые находки требуют других fixtures: nested cwd, одновременные сессии, malformed settings, failure after destructive step, foreign file ownership, dirty Git, multiple install scopes, hostile-but-valid input и current-model tool pool. Поэтому зелёные текущие тесты и настоящий дефект не противоречат друг другу.

## Что не стоит делать

- Не переписывать плагины целиком и не вводить общий lifecycle framework для трёх разных плагинов.
- Не исправлять все Low items раньше границ секретов, удаления, release и ownership.
- Не обновлять Semble до 0.5.5 только потому, что версия новее; сначала отдельно изучить changelog и совместимость.
- Не считать любое отличие от best practice багом без воспроизводимого результата.
- Не смешивать Claude Code plugin и Codex projection: это ревью относится только к Claude Code.
- Не считать обновление документации достаточным: creator instructions и прямые regression fixtures должны изменяться вместе с reference.

## Рекомендуемое решение

Репозиторий пригоден для дальнейшего точечного улучшения. Рациональный следующий шаг — не начинать исправление всех 122 пунктов, а утвердить четыре ограниченные очереди выше. Сначала обновить upstream knowledge contract и creator-агентов, затем закрыть High safety/data-loss findings, после этого унифицировать root/state/concurrency и только потом исправлять точность/переносимость.

Каждый пункт в английских отчётах уже содержит минимальный fix direction и прямой preventive test. На этапе реализации стоит брать findings небольшими группами и после каждой группы повторять именно соответствующий воспроизводящий сценарий, а не запускать бесконечный общий «улучшай всё» цикл.
