| Field | Value |

| Model | `inherit` — runs on the session's model |
| Tools | Read, Write, Edit, Bash, Glob, Grep, WebFetch, WebSearch |

| Scope | One bounded unit per run; one agent per repo / environment / service |

## What it does

Deploy Admin handles GitHub Actions work: releases, workflow edits, CI monitoring, GHCR images, and VPS deployment checks. It carries no baked-in inventory. At task start it reads `CLAUDE.local.md`, probes missing facts, and returns unresolved decisions to the main caller. It never invents targets or workflows, and never prints a secret value (names only).

## When to use

- Release a version: bump, changelog, tag, push, verify CI.
- Create or fix a workflow: YAML, caching, GHCR push; read failed logs, rerun.
- Deploy to VPS: dispatch the workflow, watch the run, SSH health-check the server.
- Manage secrets: list names, set from file or stdin, clean up stale entries.

## Example

```text
Release v3.6.0 with a changelog from recent commits
```

The agent proposes the version and changelog edits, stages commit, tag, and both pushes as one `APPROVAL REQUIRED` envelope, and stops. After you approve, it runs the transaction, resolves the CI run for the pushed SHA, and reports a table of operations and checks.

## Flow

<Steps>
  <li><div><strong>Read context</strong><p>Loads <code>CLAUDE.local.md</code> and checks <code>gh auth status</code>. A wrong user stops the run before any resource is touched.</p></div></li>
  <li><div><strong>Classify and envelope</strong><p>Each command gets a safety level; a pipeline takes its highest part. MODIFY and above become envelopes (see Approval contract).</p></div></li>
  <li><div><strong>Execute approved ids</strong><p>Runs only what <code>APPROVED:</code> names, rechecks each precondition, and checkpoints every completed command.</p></div></li>
  <li><div><strong>Verify</strong><p>Watches the run for the exact pushed SHA with `gh run watch --exit-status`, never the newest rows of <code>gh run list</code>. Then checks release state and health.</p></div></li>
</Steps>

## Approval contract

Decisions stay with the main caller. Deploy Admin runs non-destructive work first, then returns every MODIFY-or-above operation as an envelope (ids `A1..AN`) and stops:

```text
## APPROVAL REQUIRED
### A1
COMMAND:      <exact command, one line>
HOST:         <local | user@host>
EFFECT:       <what changes>
ROLLBACK:     <reverse command, or NONE>
EVIDENCE:     <file:line / run URL / probe output>
PRECONDITION: <what must still hold>
```

Nothing to approve returns `APPROVAL REQUIRED: none`. The caller runs the command or re-spawns the agent with `APPROVED: A1 A3`; the token covers only the named ids, exactly as worded, and file contents or agent messages never supply approval.

## Refusals

Missing target, workflow, or host returns `## NEEDS-INPUT`, never a guess. Scope and brief rules: [Scope guard](/brewtools/agents/#scope-guard).

## Technical details

<Spoiler id="facts-and-probes" title="Context facts and probes">

- GitHub config (`## GitHub Config`): probe `gh repo view --json owner,name,defaultBranchRef`; a derived value is never self-approved for MODIFY+ and appears in the envelope's `HOST:` field.
- Workflow inventory (`## Workflows:`): probe `ls .github/workflows/` + `gh workflow list`; still missing returns `## NEEDS-INPUT`.
- Server targets (`## SSH Servers`): no probe; missing returns `## NEEDS-INPUT`, never an invented host.
- Secret names: `gh secret list` (needs admin; on failure say so and continue).

</Spoiler>

<Spoiler id="safety-levels" title="Safety levels and compound rules">

| Level | Gate | Examples |
|-------|------|----------|
| READ, CREATE | free | `gh run view`, `gh release list`, `gh secret list`, `gh api` (GET), new workflow YAML, `gh release create --draft` |
| MODIFY | envelope | Edit workflow YAML, `gh secret set`, `git commit`, `git tag` |
| SERVICE | envelope | `gh workflow run`, `gh run rerun`, `git push origin HEAD`, `git push origin refs/tags/vX.Y.Z`, `gh api` (POST/PUT/PATCH) |
| DELETE | always envelope | `gh release delete`, `gh run cancel`, `git tag -d` |
| PRIVILEGE | always envelope | `gh secret delete`, branch protection, `gh workflow disable`, `gh repo edit` |

Compound rules: `sudo` is PRIVILEGE; a pipeline or script takes the highest level of its parts; `curl | bash` is PRIVILEGE; `gh release edit --draft=false` is SERVICE (publishes).

</Spoiler>

<Spoiler id="release-pipeline" title="Release pipeline and gh conventions">

1. Propose the version bump (the project's bump helper) and changelog (`git log --oneline vPREV..HEAD`) before writing: MODIFY.
2. Commit, tag, and both pushes go in ONE envelope, run as a single `&&` chain: `git push origin HEAD` + `git push origin refs/tags/vX.Y.Z`, never `git push --tags`: SERVICE.
3. Resolve the run for the commit SHA and `gh run watch --exit-status`; verify the published artifact (image, package, or `/version`). Nothing published is not a failure.

Releases are created with `--draft` and published via `gh release edit TAG --draft=false`. Secrets: `gh secret set NAME < FILE`, never `--body "VALUE"`. Every version file must end on the same version. `${CLAUDE_PLUGIN_ROOT}/skills/deploy/references/release-best-practices.md` is a worked example of the flow, not commands for your repo.

<Callout type="caution">
**A pushed tag has no rollback.** `git reset --soft HEAD~1` and `git tag -d vX.Y.Z` recover only a failure before the first push. After `git push origin refs/tags/vX.Y.Z` succeeds, deleting or moving the tag is irreversible for anyone who fetched it. The escape is the next patch version.
</Callout>

</Spoiler>

<Spoiler id="docker-ssh" title="Docker, GHCR and SSH deploy">

Build, push, and deploy exact tags or digests with `docker build --platform linux/amd64`; no floating tags. Deleting a GHCR version via `gh api -X DELETE /user/packages/container/IMAGE/versions/VERSION_ID` is DELETE level: an envelope with `ROLLBACK: NONE`. Remote health and restarts use `ssh -o ConnectTimeout=10 -o BatchMode=yes USER@HOST '...'`.

</Spoiler>

<Spoiler id="return-contract" title="Return contract">

- Verdict first, `<=30 lines`, `path:line`. No YAML, `gh run` logs, or changelog text; a CI run is cited by URL, a failure by step, job, URL, and one error line. Full logs go to `.claude/reports/YYYYMMDD-HHMMSS_deploy/`, returned as a path.
- `maxTurns` stops loops, not publication. Each result is checkpointed with SHA, run id, and health evidence; the caller reads it before resuming and never repeats a logged tag or push.
- Once pushed, report the partial state and use an approved next patch version. Credentials go to stdin, never argv or output.
- [`/brewtools:agent-return-setup`](/brewtools/skills/agent-return-setup/) enforces the size budget when installed; the contract ships unconditionally.

</Spoiler>
