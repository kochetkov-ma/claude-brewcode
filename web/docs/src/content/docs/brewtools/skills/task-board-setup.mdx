# task-board-setup — file-based Kanban scaffolder

<Badge variant="default" text="opus" /> <Badge variant="accent" text="status / install / upgrade / enable / disable / uninstall / purge" /> <Badge variant="accent" text="user-invoked" />

<SourceLink path="brewtools/skills/task-board-setup/README.md" anchor="task-board-setup" />

Point the skill at any repo. It analyses the domains, confirms the findings with you, then writes a file-based Kanban: curator agent, dashboard skill, lifecycle rule and the `.claude/features/**` tree. The repo stays self-contained afterwards, with no dependency on this generator.

## Quick reference

| Field | Value |
|-------|-------|
| Command | `/brewtools:task-board-setup` |
| Arguments | `[prompt] [status \| install \| upgrade \| enable \| disable \| uninstall \| purge] [target repo path \| empty = cwd] [free-text directive]` |
| No verb | A deployed board reports `status`, a fresh repo gets `install`; a bare path installs into that path |
| Model | opus |
| Emits | `task-tracker` agent, `task-board` skill, `tasks` rule, board tree, methodology, anti-drift controls; with `SPEC_MODE` also `task-spec` skill and spec templates |
| Commits | Never: committing stays a user or manager action |

## When to use

| Scenario | Command |
|----------|---------|
| Inspect what is deployed, change nothing | `/brewtools:task-board-setup status` |
| New repo needs file-based task tracking | `/brewtools:task-board-setup install` |
| Same convention in another repo | `/brewtools:task-board-setup install /path/to/repo` |
| Scattered TODO or backlog docs | `install`: sweep subagents migrate legacy docs |
| Existing board needs the spec + design layer | `/brewtools:task-board-setup upgrade /path/to/repo` |
| Pause or resume the machinery | `disable` / `enable` |
| Remove machinery, keep every task | `uninstall` |
| Remove machinery and `.claude/features/**` | `purge` |

## Example

```bash
/brewtools:task-board-setup install /path/to/some-repo also dedupe rules, skip module split
```

Expected: the skill confirms domains, exclusions and release style, writes the board, and prints a summary with the created files and passed gates. The repo then has `/task-board` (view, add, move tasks), the `task-tracker` curator, and shared methodology and anti-drift controls.

## Modes

Canonical order, shared by every `-setup` skill:

| Mode | Requires | Effect |
|------|----------|--------|
| `status` | either state | Read-only inventory: deployed or not, spec layer present, what to run next. Writes, spawns and asks nothing |
| `install` | fresh repo | Full multi-agent deploy. Refuses a repo that already has `.claude/features/board.md` |
| `upgrade` | deployed board | Adds missing controls, refreshes generated machinery, preserves task methodology, prompts and evidence |
| `enable` | deployed, parked | Renames each `.disabled` file back. No re-analysis, no subagents, no confirmation |
| `disable` | deployed board | Parks `task-tracker.md`, `task-board/SKILL.md`, `task-spec/SKILL.md` (if deployed) and `tasks.md` as `.disabled` twins. Tasks stay untouched |
| `uninstall` | deployed board | Removes the generated machinery, KEEPS `.claude/features/**` |
| `purge` | deployed board | `uninstall` plus deletion of `.claude/features/**`: every task you wrote |

## How it works

<Steps>
  <li><div><strong>Analyse the repo</strong><p>Three parallel subagents derive domains, source exclusions, release style, doc language and the repo's own agents; you confirm the findings and the `SPEC_MODE` choice via `AskUserQuestion`.</p></div></li>
  <li><div><strong>Generate the curator and dashboard</strong><p>Writes `task-tracker` (writes only under `.claude/features/**`) and the `task-board` skill, plus `task-spec` when `SPEC_MODE` is on.</p></div></li>
  <li><div><strong>Generate the rule and scaffold</strong><p>Writes `.claude/rules/tasks.md` and the folder tree; it never edits the target's `CLAUDE.md`.</p></div></li>
  <li><div><strong>Sweep legacy docs</strong><p>Bounded subagents migrate old backlog and feature docs into `closed/` and `backlog/`. No legacy docs means no sweep.</p></div></li>
  <li><div><strong>Optional CLAUDE.md pass</strong><p>Propose-only, opt-in, and asks before every change. Declining writes nothing.</p></div></li>
</Steps>

<Callout type="note">
Board generation never reverses an accepted CLAUDE.md edit when you later uninstall. Blocks between another tool's begin/end markers (for example `BEGIN brewcode:semble`) stay untouched and are reported as `managed by <setup>`.
</Callout>

Delegation: each spawn gets one bounded unit under the six-field brief, see [Delegation](/brewcode/skills/#delegation).

| Artifact | Path | Role |
|----------|------|------|
| Curator agent | `.claude/agents/task-tracker.md` | Owns the board: create, move, close, groom; keeps `board.md` canonical |
| Dashboard skill | `.claude/skills/task-board/SKILL.md` | On-demand `/task-board`: view, add, move, backlog, groom |
| Paths-scoped rule | `.claude/rules/tasks.md` | Lifecycle, id convention, required frontmatter, run-at-task-start rule; auto-loads on `.claude/features/**` |
| Board file | `.claude/features/board.md` | Counts and task table |
| Session progress | `.claude/features/PROGRESS.md` | Five fields, overwritten in place; written in both `SPEC_MODE` states |
| Methodology | `.claude/features/METHODOLOGY.md` | Domain risks, review strategy, reliable check commands |
| Anti-drift | `.claude/features/ANTI-DRIFT.md` | Tick prompts, timer lifecycle, reconciliation, reporting contract |
| Task graph | `.claude/features/task-graph.md` | Derived dependencies, owners, statuses, evidence |
| Control files | `.claude/features/{TRACKER,TASK_TEMPLATE,INDEX}.md` + `backlog/README.md` | Tracker log, template, index, backlog guide |
| Folders | `.claude/features/{backlog,todo,progress,closed,specs}/` | Folder name = task status |
| Spec skill (`SPEC_MODE`) | `.claude/skills/task-spec/SKILL.md` | On-demand `/task-spec <ID>` |
| Spec templates (`SPEC_MODE`) | `.claude/features/specs/{SPEC_TEMPLATE,DESIGN_TEMPLATE}.md` | Section skeletons for the two spec documents |

<Spoiler id="task-methodology-and-session-anti-drift" title="Task methodology and session anti-drift">

Installed in both spec modes. Shared methodology comes from your domain and repository instructions. Every accepted task specializes it in its own `## Methodology`: goal, acceptance criteria, domain reviews and tests, base work units, owners, dependencies, parent id.

Baseline work: confirm scope and corrections, assign bounded work, implement, simplify, review correctness and safety, review clarity and missing validation, run reliable checks, reconcile evidence and the board.

**One session timer per active top-level task.** The main session's `/task-board` flow owns timer creation and cleanup; `task-tracker` returns scheduling actions to it. Each top-level task stores a unique prompt in `## Anti-drift cron`; queued tasks keep prepared prompts and scheduling starts when a task becomes active. Child work units use the parent's timer.

- Default schedule is hourly (`0 * * * *`); your cadence override or opt-out wins.
- It lists existing timers first, reuses a matching one, and announces cadence, timezone, timer id and state, first due time, scope, and stop/change controls.
- It uses `CronList`, `CronCreate` and `CronDelete`. With those tools unavailable, denied or full, it keeps the prompt and reports that scheduling is unavailable.
- Timers are session-scoped and delivery time is approximate. Saved ids do not prove a timer is live.

**Each delivered tick:**

- Rereads methodology, anti-drift controls, goal or spec, task records and user corrections.
- Gets concise evidence from active agents; reconciles statuses, dependencies, counts and next work.
- Rebuilds `task-graph.md` with every unfinished node and the latest ten completed ones; older evidence moves to task Notes or closed records first.
- Checks drift against acceptance criteria, corrects within authorized scope, quantifies remaining work or marks it unknown.
- Persists the tick number and receipt time, then reports at most five compact lines.

```text
🔵 TASK-ID · 14:03 Europe/Lisbon · tick 2 · elapsed 2h
🟢 Implemented API change; targeted checks pass
🔵 2 work units remain · next: independent review
🔴 Blocker: missing fixture · question: provide approved sample?
⚪ Drift: none verified against recorded acceptance criteria
```

Completion, cancellation or parking stops this task's timers and verifies their absence; a failed deletion stays a reported cleanup gap.

**Planning and `+++`.** Plan mode stays read-only: the plan carries methodology, base work, graph reconciliation, the task prompt, a timer execution step and a final PROGRESS refresh. Timers and file writes wait for authorized execution. With the brewmod-placeholders mod (Claude Code 2.1.292+), typing `+++` in Plan mode injects this requirement through the default `+` placeholder (`when: plan`); outside Plan mode it adds no cron instruction. See [mods](/mods/overview/).

</Spoiler>

<Spoiler id="session-progress-progress-md" title="Session progress (PROGRESS.md)">

`board.md` owns the task list; `PROGRESS.md` owns what the session did about it. It is not a second board.

| Field | Holds |
|-------|-------|
| `Updated` | ISO date of the last rewrite |
| `In flight` | Task ids being worked now |
| `Moved since last update` | `<ID>: todo -> progress`, one line each |
| `Blocked` | `<ID>: what blocks it / who unblocks it` |
| `Next` | The single next action |

It loads through a rule, not a hook: `tasks.md` carries `paths: [".claude/features/**"]`, and `PROGRESS.md` lives under that glob.

| # | Rule |
|---|------|
| P1 | Always exists; missing means recreate from `board.md` first |
| P2 | The main session refreshes it in the same change as any transition |
| P3 | Plan mode: a plan touching any task ends with `update .claude/features/PROGRESS.md` |
| P4 | `task-tracker` rewrites the five fields every run and reports staleness; act on its `NEXT:` line yourself |

**Board drain.** When the `progress` count reaches zero, `task-tracker` appends `NEXT: run /brewtools:task-board-setup upgrade <path>`, only when the repo has no `.claude/skills/task-spec/`.

</Spoiler>

<Spoiler id="spec-design-layer-spec-mode" title="Spec + design layer (SPEC_MODE)">

Optional, confirmed in the Step 1 question. With `SPEC_MODE=off` the spec artifacts are omitted; methodology, graph, progress and anti-drift stay.

| Doc | Path | Owns |
|-----|------|------|
| Task | `.claude/features/{backlog,todo,progress,closed}/<ID>.md` | WHAT + WHY, with a `## Scope` table of blocks `S1..Sn` |
| Product spec | `.claude/features/specs/<ID>-spec.md` | HOW: decisions `D1..Dn`, questions `Q1..Qn`, coverage matrix |
| Design spec | `.claude/features/specs/<ID>-design.md` | Components, data flow, interfaces, failure modes, non-goals |

Every task gains `spec: none | pending | full | design-only`. A task needs a spec when it touches more than one domain or ~5 files, adds an integration, changes a schema or contract, is ambiguous, or the user asked for a design.

| Entry | Form |
|-------|------|
| Explicit | `/task-spec <ID>` (default `full`), `/task-spec <ID> design`, `/task-spec <ID> refresh` |
| Plain prose | "architect this task", "write the spec" |
| Redirect | `task-tracker` ends with `NEXT: run /task-spec <ID> (spec required: <reason>)` |

For each touched domain `task-spec` walks a 4-link agent chain, spawned in one message: team agent, project domain agent, any architecture-capable project agent, built-in `Plan`. A refusing agent re-delegates to the colleague it names, capped at 2 retries.

| Gate | Rule |
|------|------|
| G1 coverage | Every `in` scope id is `covered` in both tables; `partial` or `uncovered` keeps `status: draft` |
| G2 close | `progress -> closed` is blocked while a `blocking: yes` question is open; override with `SPEC WAIVER: <reason>` in `## Notes` |
| G3 sync | Editing `## Scope` invalidates both specs to `draft`; run `refresh` |
| G5 staleness | Report-only `SPEC STALE: <ID>` plus one `NEXT:` line; never blocks the close |

Before the architect fan-out, one `AskUserQuestion` pass (3-5 questions) covers Scope, Constraints and Edge cases; answers land in `## Original requirements` and `## User Q&A`. More than 3 domains or 12 `in` ids makes the report propose a split for `task-tracker`.

`-n` / `--noask` skips the clarify pass (P0.7), the open-questions batch (P5) and review escalation (P6-C), each recorded as `Skipped (--noask mode)`. Blocking questions stay blocking; an ambiguous task id and a missing `## Scope` still stop and ask.

Self-review loop: A finds (one adversarial reviewer per domain), B verifies each finding, C fixes confirmed blockers and majors, capped at 3 iterations. Survivors go to the user; under `--noask` they become blocking questions. The final report (P7) is a fixed block: mode, domains and agents, docs written, decision and question counts, G1 verdict, review counts, size advisory.

</Spoiler>

<Spoiler id="upgrading-an-existing-board" title="Upgrading an existing board">

`/brewtools:task-board-setup upgrade <path>` retrofits a repo that already has `.claude/features/board.md`; `install` refuses that repo and points here.

| Layer | Gate | Adds |
|-------|------|------|
| Spec layer | `SPEC_MODE`, forced `on` | `task-spec` skill, both templates, spec-related sites in existing files |
| Session progress | ungated | `PROGRESS.md` plus every reference to it |
| Methodology and anti-drift | ungated | Methodology, anti-drift, task graph, template sections |

- Every edit to an existing file is shown as a diff and gated by `AskUserQuestion`; declined means no edit.
- Task ids, scope ids and board rows are never renumbered, reordered or deleted. The one allowed `board.md` edit appends a `spec` cell (`--`) to existing progress and todo rows.
- Backfilling `spec:` is opt-in and off by default; the value is `pending` or `none`, never `full`.
- Domains, exclusions and language are recovered from deployed artifacts; only the domain-agent inventory re-runs.
- Provenance refresh is reported separately and does not prove that content changes were accepted.

</Spoiler>

<Spoiler id="technical-details" title="Technical details: output, ids, versions, references">

**Curator output.** `task-tracker` returns a verdict plus task ids and `file:line` pointers, never the board or task bodies. Long logs and dumps go to `.claude/reports/<YYYYMMDD-HHMMSS>_<name>/` and only the path returns.

**ID convention.** `<PREFIX>-<DOMAIN>-<SLUG>` in `UPPER-KEBAB`; `<DOMAIN>` is a first id-segment confirmed in Step 1.

| Prefix | Use |
|--------|-----|
| `T-` | Feature or product task |
| `BUG-` | Defect |
| `M-` | Maintenance, refactor, tech debt |
| `EPIC-` | Umbrella over several tasks |

**Content version and ownership.** With the spec layer, twelve control artifacts carry `doc_type: llm` and the provenance quartet `version`, `content_version`, `generated_by: "brewtools:task-board-setup"`, `last_updated`: the agent, the `task-board` and `task-spec` skills, `tasks.md`, and eight files under `.claude/features/` (`board.md`, `TRACKER.md`, `INDEX.md`, `PROGRESS.md`, `backlog/README.md`, `METHODOLOGY.md`, `ANTI-DRIFT.md`, `task-graph.md`). `TASK_TEMPLATE.md` and task cards carry no stamps. `/brewcode:setup-status` compares the `content_version` of `board.md` with the generator's. Every `upgrade` refreshes only the quartet in existing frontmatter.

**Placeholders** substituted before writing: `{{DOMAINS}}`, `{{FIRST_DOMAIN}}`, `{{EXCLUSIONS}}`, `{{REPO_NAME}}`, `{{LANG}}`, `{{TODAY}}`, `{{CLOSE_MARKER}}` / `{{CLOSE_MARKER_SHORT}}` (from `RELEASE_STYLE`: `vtag`, `sha`, `none`), plus `{PLUGIN_VERSION}`, `{CONTENT_VERSION}`, `{GENERATED_BY}`, `{LAST_UPDATED}`.

**Reference files** in `${CLAUDE_SKILL_DIR}/references/`: `01-analysis.md`, `02-task-tracker-agent.md`, `03-task-board-skill.md`, `04-tasks-rule.md`, `05-features-templates.md`, `06-doc-sweep.md`, `07-claude-md-optimize.md`, `08-task-spec-skill.md`, `09-spec-templates.md`, `10-upgrade.md`, `11-methodology-cron.md`.

</Spoiler>
