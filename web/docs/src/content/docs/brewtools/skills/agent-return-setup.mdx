# Agent Return Setup — size budget for subagent returns

<Badge variant="primary" text="sonnet" /> <Badge variant="accent" text="status / install / upgrade / enable / disable / uninstall / purge" /> <Badge variant="secondary" text="project | global" /> <Badge variant="accent" text="opt-in" /> <Badge variant="accent" text="user-invoked" />

## What it does

Subagent returns are the largest single context cost in a manager session. The rule "verdict first, at most 30 lines, <code>path:line</code>" already existed as prose and was ignored — a rule sitting at the top of context loses to whatever the agent just did. `/brewtools:agent-return-setup` restates that rule mechanically, at the exact moment it bites.

It installs three hook files sharing one module, wired as three registrations: a <code>SubagentStart</code> contract hook injects the return rule as advisory context, and one guard file sizes the final message against two thresholds on two events — <code>SubagentStop</code> (classic path) and <code>PreToolUse</code> with matcher <code>SubagentHandback</code> (auto-mode hand-back path). No LLM judge anywhere — the decision is a plain number comparison.

Run the skill with no arguments and it reports status first — installed scopes, wired hooks, current thresholds — before doing anything else. Every mode, including <code>status</code>, prints the 5-field PLAN block up front; the mutating ones (<code>install</code>, <code>upgrade</code>, <code>enable</code>, <code>disable</code>, <code>uninstall</code>, <code>purge</code>) then ask only what is still unknown before delegating the file and settings work to the <code>brewcode:hook-creator</code> agent. The feature is **opt-in** — these hooks are not registered in <code>brewtools/hooks/hooks.json</code>, so installing the plugin does nothing until this skill runs.

## When to use

| Situation | Suggested invocation |
|-----------|----------------------|
| Manager sessions losing context to bloated subagent reports | `/brewtools:agent-return-setup install` |
| Same budget on every project on this machine | `/brewtools:agent-return-setup install global` |
| Pick up a new hook version after a brewtools update, same thresholds | `/brewtools:agent-return-setup upgrade` |
| Check what is currently installed without changing anything | `/brewtools:agent-return-setup status` |
| Temporarily stop enforcing without removing files | `/brewtools:agent-return-setup disable` |
| Fully remove hooks, settings entries and config | `/brewtools:agent-return-setup purge` |

## Example

```
/brewtools:agent-return-setup install project 2500 6000
```

Expected flow: the skill prints the current status table, states the plan ("copy 3 files into <code>.claude/hooks/</code>, write <code>.claude/agent-return.json</code> with <code>passTokens: 2500</code>, <code>fileTokens: 6000</code>, merge 3 settings.json entries"), asks nothing — scope and both thresholds are already supplied, so the question step is skipped entirely, delegates to <code>brewcode:hook-creator</code>, then re-prints the status table showing <code>hook_files=3/3 settings_refs=2 enabled=true registrations=3/3</code>.

## Technical details

### The three files

| File | Event | Behavior |
|------|-------|----------|
| `agent-return-budget.mjs` | — | Shared module: config discovery, threshold resolution, read-only list, report dir, `estimateTokens`, the contract text. **Never registered in settings.json** — imported by both hooks, so the announced budget and the enforced budget can never drift apart |
| `agent-return-contract.mjs` | `SubagentStart` (matcher-less) | Injects the return contract as `additionalContext`. Advisory only, no decision |
| `agent-return-guard.mjs` | `SubagentStop` (matcher-less) | Classic path: sizes `last_assistant_message`, blocks at most once with a compress, file or essential-part order |
| `agent-return-guard.mjs` (same file) | `PreToolUse`, matcher `SubagentHandback` | Auto-mode path (Claude Code 2.1.271+): sizes `tool_input.message`, denies the hand-back at most once. Older versions have only the classic path |

All three install as a unit. ESM resolution runs before evaluation, so a hooks dir holding 2 of the 3 files exits 1 with an empty stdout and a hook-error banner on every subagent spawn and return — never copy 2 of 3.

Sizing tiers, `t = Math.ceil(<report text>.length / 4)`, both boundaries inclusive on the low side:

| Range | Decision | Order |
|-------|----------|-------|
| `t <= passTokens` (default 2500) | pass | none |
| `passTokens < t <= fileTokens` (default 6000) | block | **compress** — re-send the same answer, keep the verdict and every `path:line`, drop preamble/bodies/output/logs/restated context, no new work |
| `t > fileTokens`, agent can write | block | **file** — write the full report to `<project root>/<reportDir>/YYYYMMDD-HHMMSS_<agent-slug>-<run-id>/` (`reportDir` default `.claude/reports`), then answer with that path plus verdict plus a summary within the budget. A denied write is never retried: a compressed inline report instead |
| `t > fileTokens`, agent cannot write (plan mode, or a type in `readOnlyAgentTypes`) | block | **essential part** — no file; verdict, findings the caller must act on, key `path:line` refs, one line naming what was left out |

**Challenged at most once per agent, across both paths** — before a challenge the guard creates a marker `agent-return-state/<sha256(agent_id)>.json` beside the config (pruned after 24 h), and `stop_hook_active === true` is checked before any sizing. A compress round that lands slightly over `passTokens` (observed live: 1417 -> 1026 est-tokens against a budget of 1000) is not challenged a second time. A payload without `agent_id` (main session, internal agents) is never challenged. Deliberate trade: repeated hand-back denies make the harness withhold the report, and the once-only guarantee outranks the last few percent.

### Modes

| Mode | Effect | Hook files | settings.json | Config |
|------|--------|-----------|----------------|--------|
| `status` (default with empty input) | report only | — | — | — |
| `install` | wire + configure | 3 copied | 3 entries merged | written |
| `upgrade` | re-emit from the current plugin version, thresholds preserved | 3 re-copied | entries re-merged (adds the `SubagentHandback` entry an older install lacks) | values preserved, metadata re-stamped |
| `enable` | resume enforcement | kept | kept | `enabled: true` |
| `disable` | pause enforcement | kept | kept | `enabled: false` |
| `uninstall` | unwire | deleted | entries stripped (an emptied `settings.json` and hooks dir are removed) | **kept** (see [Orphan project config](#orphan-project-config)) |
| `purge` | full wipe | deleted | entries stripped | deleted (an emptied project `.claude/` is removed too; never the global dir) |

`upgrade` asks nothing: it reads `passTokens`/`fileTokens` back out of the existing config and replays the install for that scope against the current assets, so a plugin update finally reaches an installed project without re-asking. A disabled setup stays disabled. It migrates one pair once: exactly `1000` / `2500` with no `readOnlyAgentTypes` key (the pre-6.5 defaults) becomes `2500` / `6000`. One scope per run.

### Orphan project config

`uninstall project` keeps `.claude/agent-return.json` by design. When the global scope still registers the hooks, that kept file keeps governing them: the nearest project config is read before the global one, so its `passTokens`, `fileTokens` and `enabled` override the global config. In that case the uninstall prints `WARNING: kept <cfg> still GOVERNS ...`; the skill relays it verbatim and offers `purge project` in the same confirmation.

`status` reports it with three fields:

| Field | Meaning |
|-------|---------|
| `governing_config` / `governing_scope` | the one config every wired hook reads (resolution: see Config discovery below); scope is `project`, `global` or `none` |
| `orphan_config` | `yes` when the governing config is project-side, the project has `0/3` registrations and the global scope has at least one |

An orphan is reported as a finding, not as stale. Fix: `/brewtools:agent-return-setup purge project` deletes the file, and the global config governs again. Keeping it on purpose is valid. `upgrade` is never offered for it, because it would re-wire the project hooks and undo the uninstall.

### Installation targets

| Scope | Hooks dir | settings.json | Config |
|-------|-----------|----------------|--------|
| Project | `<repo>/.claude/hooks/` | `<repo>/.claude/settings.json` | `<repo>/.claude/agent-return.json` |
| Global | `<config dir>/hooks/` | `<config dir>/settings.json` | `<config dir>/agent-return.json` |

`<config dir>` is the one Claude Code runs with: `$CLAUDE_CONFIG_DIR` when set, else `~/.claude/`. The project scope is the session's start directory (what hooks receive as `CLAUDE_PROJECT_DIR`); from a repo subdirectory the git root's `settings.json` is not loaded. The state directory `agent-return-state/` sits beside the config that enabled the feature.

Config discovery starts at the resolved project root (`CLAUDE_PROJECT_DIR`, then an upward walk from the cwd for a `.git` or `.claude` marker, never the git toplevel, then cwd), walks up 16 levels probing `<dir>/.claude/agent-return.json`, then falls back to `$CLAUDE_CONFIG_DIR/agent-return.json` when set, then `~/.claude/agent-return.json`. Project wins, even when the project has no hooks wired; a malformed project config is skipped and the climb goes on; global only when no valid project config is found. Global writes go through Bash only — the config dir is a protected path for `Write`/`Edit`: prompted in `default` and `acceptEdits`, denied headless and in `dontAsk`, allowed only under `bypassPermissions`.

### Config shape

```json
{
  "enabled": true,
  "passTokens": 2500,
  "fileTokens": 6000,
  "readOnlyAgentTypes": ["Explore", "Plan"],
  "version": "X.Y.Z",
  "content_version": "X.Y.Z",
  "generated_by": "brewtools:agent-return-setup",
  "last_updated": "YYYY-MM-DD"
}
```

| Key | Meaning |
|-----|---------|
| `enabled` | must be exactly `true`; anything else, or no config at all, turns both hooks into no-ops — the enable/disable mechanism |
| `passTokens` | pass ceiling, the number quoted as `budget` in every order; positive integer; default `2500` |
| `fileTokens` | compress/file tier boundary; positive integer; default `6000` |
| `readOnlyAgentTypes` | agent types without a file-writing tool, matched exactly on `agent_type` (plugin agents as `plugin:name`): over `fileTokens` they are asked for the essential part, not a file. Any array replaces the default `["Explore","Plan"]`; `[]` = nobody |
| `reportDir` | optional, added by hand; where the file tier writes. Relative = under the project root, absolute as is, `~/` = under `$HOME`; absent or blank = `.claude/reports` |
| `version` / `content_version` / `generated_by` / `last_updated` | Provenance restamped on install, upgrade, enable, and disable; content_version tracks changed generator content, while version identifies the producing plugin release |

**Threshold precedence, per threshold, first hit wins:** the config key — the env var (`AGENT_RETURN_PASS` / `AGENT_RETURN_FILE`, parsed with `Number()` not `parseInt()`) — the built-in `2500` / `6000`. Only a positive integer is accepted at either level; `1.7`, `abc`, `-5`, `0`, `NaN`, `Infinity` all fall through.

Config values are read on every hook call — changing `enabled`, a threshold, the list or `reportDir` takes effect immediately, no restart. Hook **wiring** changes also apply to the running session, with no restart.

Setup-status compares each artifact's content_version with the source for that artifact,
then corroborates copied hook bytes and ownership. Hook and config-generator content versions
can differ, and unchanged content need not match a newer plugin release number. A missing
comparison source is reported as unknown, not a fabricated stale verdict.

### Why 2500 / 6000

Measured over 80 real Agent returns across 4 session transcripts, sized `chars/4`:

| p10 | p25 | p50 | p75 | p90 | max |
|-----|-----|-----|-----|-----|-----|
| 502 | 761 | 1404 | 2256 | 3164 | 7931 |

Total 136.7k est-tokens, of which 79.4k (58%) is overflow above 800 — preamble, restated context, pasted file bodies, command output, logs. `2500` is roughly p78, so only the heaviest fifth of returns is challenged. `6000` sits between p90 and the maximum and is a judgement call, not a fit: below it one compression round can still reach the budget, above it the detail needs a durable home.

Live proof, measured at the pre-6.5 thresholds (1000 / 2500), one real session, two blocked returns each blocked exactly once: `1417 -> 1026` est-tokens (compress tier) and `2585 -> 245` est-tokens citing a report path (file tier) — 2731 est-tokens of manager context saved across two returns.

<Callout type="warning">
**Honest limits — read before relying on this.**

- **`chars/4` is not a tokenizer, on purpose.** The thresholds were fitted to a distribution measured with `chars/4`. Swapping the heuristic moves the boundaries off the data — re-measure and re-fit both in the same change.
- **Only the final assistant message is sized.** A subagent that burned context on 40 tool calls and returns 6 lines is invisible to this guard — it budgets the return, not the work.
- **`passTokens < fileTokens` is not enforced by the hook itself.** Inverting them degrades gracefully — the compress tier vanishes and everything over `passTokens` gets a self-contradictory file order; no loop, no error, exit 0. The config write step rejects the inversion; the hook carries no validator.
- **The default `reportDir` is a protected path.** `.claude/reports` costs the file tier a permission check: prompted in `default` and `acceptEdits`, routed to the classifier in `auto`, denied in `dontAsk` and headless runs, allowed in `bypassPermissions`; `permissions.allow` rules do not pre-approve it. The agent then returns a compressed inline report. For unattended runs set `reportDir` outside `.claude/`.
- **No hook payload exposes an agent's tool inventory.** Write ability is known only from `readOnlyAgentTypes` and plan mode; add unlisted read-only agent types to the list.
- **Fail-open everywhere, never exit 2.** The guard blocks through JSON output, not an exit code. Malformed JSON, missing stdin, wrong shapes, any runtime throw -> `{}` and exit 0.
- **A missing `agent-return-budget.mjs` is not catchable** — the hook exits 1 with empty stdout, a non-blocking hook-error banner (see the unit rule above).
- **Cost: no per-tool-call tax.** Measured on Node v24.19.0, 15 invocations each, wall clock including node startup: about 30-53 ms per fire, at spawn, at each stop and, in auto mode, at the hand-back — node startup dominates, message size barely registers. Registered timeout is 5 s. Unlike `agent-deadline-setup`, whose guard sits on a `.*` PreToolUse matcher and taxes roughly 58 ms on every tool call, this pair fires only at subagent spawn, stop and hand-back, so a **global install is cheap**. Numbers are from one machine — re-measure before quoting them as facts.
</Callout>

### Coexistence with `agent-deadline-setup`

Both skills install side by side. Both register `SubagentStop` and `PreToolUse` entries; hooks of one event run in parallel, and each skill's merge and strip only touch entries naming its own scripts. An agent challenged once by this guard continues on its original deadline clock, and the deadline guard always allows `SubagentHandback`. An agent-deadline install from before 6.5 also denies the hand-back past its limit, so upgrade it too.
