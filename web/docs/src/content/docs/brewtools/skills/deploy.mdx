# deploy — GitHub Actions CI/CD

<Badge variant="primary" text="opus" /> <Badge variant="accent" text="human-invoked" />

Creates workflows, cuts releases, triggers deployments and watches runs, with a confirmation gate before every write or push. Run it with no arguments: no config yet starts setup, an existing config opens monitor.

## Quick reference

| Field | Value |
|-------|-------|
| Command | `/brewtools:deploy` |
| Arguments | `[prompt] [setup\|create\|release\|deploy\|monitor\|update-agent]` |
| Model | opus |
| Config | `CLAUDE.local.md` (gitignored) |
| Agent | [deploy-admin](/brewtools/agents/deploy-admin/) |

## Modes

| Mode | Does |
|------|------|
| `setup` | Detect repo, list workflows and secrets, write config, generate `deploy-admin` |
| `create` | Generate workflow YAML from a template (Build+GHCR, Deploy VPS, Release, Security Scan) |
| `release` | Probe tooling, plan, confirm, bump, commit + tag + push, watch CI, verify artifact |
| `deploy` | Pick a `workflow_dispatch` workflow, confirm, trigger, watch the run |
| `monitor` | Recent runs, workflow states, releases, failed-run logs |
| `update-agent` | Re-discover workflows, regenerate `deploy-admin` |

## Example

```bash
/brewtools:deploy release patch
```

The skill probes release tooling, shows the plan, asks for approval, then runs the approved commit, tag and push chain and watches every CI run of the pushed commit.

## How it works

<Steps>
  <li><div><strong>Detect mode</strong><p>An explicit mode token wins; otherwise keyword hits decide. Conflicts require clarification.</p></div></li>
  <li><div><strong>Check environment</strong><p>Verifies `gh` auth, scopes and repo, then loads the GitHub config from `CLAUDE.local.md`.</p></div></li>
  <li><div><strong>Set up (first run)</strong><p>Writes the config, gitignores `CLAUDE.local.md`, generates `deploy-admin`.</p></div></li>
  <li><div><strong>Classify and confirm</strong><p>READ and CREATE run freely. MODIFY, SERVICE, DELETE and PRIVILEGE always ask first.</p></div></li>
  <li><div><strong>Operate and monitor</strong><p>Create, release or deploy runs after approval, then monitor reports run states and failed logs.</p></div></li>
</Steps>

## Good to know

<Callout type="caution">
Every destructive operation requires explicit confirmation. Compound commands are split into individually classified steps.
</Callout>

<Callout type="warning">
Local recovery does not undo publication. After the HEAD push the commit is public; after the tag push consumers may have fetched it. Use an approved next patch version rather than moving public history.
</Callout>

## Technical details

<Spoiler id="release-probe" title="Release mode: nothing assumed about your repo">

Step 0 lists `.claude/scripts/*.sh`, `scripts/`, the `package.json` scripts and `Makefile`, then records three values, each defaulting to `none`:

| Value | Holds |
|-------|-------|
| `BUMP_SCRIPT` | a bump/version script |
| `POST_SCRIPT` | a post-release/publish script |
| `CHANGELOG` | `CHANGELOG.md` or `RELEASE-NOTES.md` |

`none` is not a failure: the step is skipped or done by hand, and the report says so. Bump and changelog changes are proposed before any write. Verify checks whatever the project publishes (image, package, `/version` endpoint); nothing published reports "no external artifact to verify". `references/release-best-practices.md` holds a worked example to adapt, not commands to run.

</Spoiler>

<Spoiler id="safety-classification" title="Safety classification and templates">

Risk classes (READ, CREATE, MODIFY, SERVICE, DELETE, PRIVILEGE) and their gates: [deploy-admin safety levels](/brewtools/agents/deploy-admin/#safety-levels).

| Template | Trigger |
|----------|---------|
| Build + Push GHCR | tag / branch |
| Deploy to VPS | `workflow_run` / `workflow_dispatch`, release-tag images only, health check, rollback |
| Release | tag `v*.*.*` |
| Security Scan | push / PR, SARIF upload |

All templates pin `runs-on: ubuntu-24.04`. The Deploy template rejects branch-built images before any server copy and logs in to GHCR with the job token over stdin.

</Spoiler>

<Spoiler id="config-and-limits" title="Config, SSH integration and limits">

- Config and workflow inventory live in `CLAUDE.local.md`. Secret names are stored, values are never read or written.
- VPS targets come from the SSH inventory written by the [ssh](/brewtools/skills/ssh/) skill: run `/brewtools:ssh setup` first.
- Limits: 2 retries per operation, 15 `gh` calls per invocation, 30 s per `gh` command, 15 min for `gh run watch`.
- CI runs are matched by the pushed commit's `headSha`; unmatched or timed-out runs are reported, never treated as success. Transaction failures keep their nonzero exit and stop later steps; RELEASED is emitted only after every approved step succeeds.
- Run `update-agent` after workflow or config changes.

</Spoiler>

<Spoiler id="delegation" title="Delegation">

For a bounded unit the skill spawns [deploy-admin](/brewtools/agents/deploy-admin/), one per repo or environment, with the six-field brief described in [Delegation](/brewcode/skills/#delegation). Confirmation gates stay in the main conversation; the agent returns exact approval envelopes and runs only the APPROVED ids.

</Spoiler>

<Spoiler id="troubleshooting" title="Troubleshooting">

| Issue | Fix |
|-------|-----|
| `gh` not installed | Install from https://cli.github.com/ |
| Not authenticated | `! gh auth login` |
| Insufficient scopes | `! gh auth login -s repo,workflow,write:packages` |
| Workflow not triggering | Check the trigger and branch/tag pattern in the YAML |
| Release CI failed | `/brewtools:deploy monitor` |
| VPS deploy failed | `/brewtools:ssh connect to server-name` |

</Spoiler>
