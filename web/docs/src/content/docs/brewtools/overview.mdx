# Brewtools Overview

Brewtools is a lightweight plugin providing universal utilities: token-efficient optimization,
AI-artifact removal, secrets scanning, SSH server management, and GitHub Actions deployment.
Each skill is self-contained and requires no prior setup.

<Callout type="note" title="The -setup naming rule">
  A `-setup` suffix marks a skill that **installs a mechanism you afterwards use instead of the skill** -- hooks, a generated Kanban, a delegation wall. Recurring tools you run again and again keep bare names (`text-optimize`, `deploy`, `ssh`). Every `-setup` skill shares one canonical mode set, in this order: `status | install | upgrade | enable | disable | uninstall | purge`. No argument means `status` when it is installed and `install` when it is not.
</Callout>

<Callout type="warning" title="v6 hardening">
  The HARD delegation wall (`manager-setup`) moved from a denylist to a strict per-binary allowlist that fails closed on any flag it does not recognize, and closed four further bypasses: `git diff --output=`, `git branch -D`, `gh issue comment --body`, `find -fprint0`. Every subagent lost `AskUserQuestion` (removed in Claude Code 2.1.233) -- a destructive or privileged step now returns a `## APPROVAL REQUIRED` envelope to the caller instead of asking directly. `ssh-admin` no longer places secrets on `curl` argv.
</Callout>

## Artifact metadata

Every `-setup` skill stamps what it writes with the plugin version that generated it and `generated_by` naming the skill. JSON artifacts carry these plus `last_updated` as top-level keys. The byte-copied `.mjs`/`.md` hook and prompt files carry only `version` and `generated_by` in a `// brewcode-meta:` comment line (or `.md` frontmatter) -- never `last_updated`, since the date would be the release date already present at the top of the file and rewriting it on every build would defeat the copy's own drift check.

| Skill | Carrier |
|-------|---------|
| [manager-setup](/brewtools/skills/manager-setup/) | `state.json` top-level keys + the copied guard's `brewcode-meta` line |
| [think-short-setup](/brewtools/skills/think-short-setup/) | `brewcode-meta` line in each of the three `.mjs` hooks + the prompt file |
| [agent-deadline-setup](/brewtools/skills/agent-deadline-setup/) | `agent-deadline.json` top-level keys + both hooks' `brewcode-meta` line |
| [agent-return-setup](/brewtools/skills/agent-return-setup/) | `agent-return.json` top-level keys + the `brewcode-meta` line in all three `.mjs` |
| [agent-router-setup](/brewtools/skills/agent-router-setup/) | `agent-router.json` top-level keys + the hook's `brewcode-meta` line |
| [task-board-setup](/brewtools/skills/task-board-setup/) | `.md` frontmatter (`doc_type: llm`, `version`, `generated_by`, `last_updated`) on nine generated artifacts |

`/brewcode:setup-status` reads these stamps back across all eleven `-setup` skills in this marketplace and tells you when an install is running on an older brewtools version than the plugin currently installed — the fix is always that skill's own `upgrade` mode.

## Plugin variable

`${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_SKILL_DIR}` are text substitutions Claude Code performs
on the prompt itself, not environment variables -- no hook injection required.
Skills in the main conversation use `${CLAUDE_SKILL_DIR}` to access their own files.
Subagent `.md` definitions get `${CLAUDE_PLUGIN_ROOT}` substituted into the prompt text at
Task spawn; it is not readable as a shell variable inside a Bash call.

## Architecture

```
brewtools/
├── .claude-plugin/
│   └── plugin.json              # Plugin manifest
├── hooks/                       # filenames deliberately NOT renamed in v5.0.0
│   ├── hooks.json               # Hook registry
│   ├── session-start.mjs        # SessionStart: HARD-wall awareness, manager codeword prep
│   ├── manager-prompt.mjs       # UserPromptSubmit: ++m / ++a / ++rr / ++r codewords
│   ├── hardmode-guard.mjs       # Copied into a project by manager-setup install
│   └── lib/                     # utils.mjs, manager-state.mjs, manager-prompts.mjs
├── skills/
│   ├── text-optimize/           # Token optimization
│   ├── text-human/              # AI artifact removal
│   ├── secrets-scan/            # Secrets scanning
│   ├── ssh/                     # SSH server management
│   ├── deploy/                  # GitHub Actions deployment
│   ├── plugin-update/           # Check, install, and update plugin suite
│   ├── provider-switch/         # Alternative API provider management
│   ├── agent-deadline-setup/    # Soft wall-clock budget for subagents
│   ├── agent-return-setup/      # Size budget on every subagent's final return
│   ├── agent-router-setup/      # Generic-spawn router (experimental)
│   ├── manager-setup/           # Hard delegation wall + codewords
│   ├── task-board-setup/        # File-based Kanban generator
│   └── think-short-setup/       # Terse-mode hook installer
└── agents/
    ├── text-optimizer.md        # Text optimization agent
    ├── ssh-admin.md             # SSH server administration
    └── deploy-admin.md          # GitHub Actions, CI/CD agent
```

<Callout type="note" title="Brewtools vs Brewcode">
  **Brewtools** provides standalone text utilities: optimization, humanization, security scanning.
  Each skill works independently with no lifecycle dependencies.

  **Brewcode** is the spec-and-search plugin -- agent and skill authoring, semantic code
  search via the semble MCP, deep-review and team generators, plus the cross-plugin
  setup dashboard.

  Both plugins install from the same `claude-brewcode` marketplace but operate independently.
</Callout>
