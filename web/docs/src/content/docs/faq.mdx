# FAQ

<Spoiler id="update-plugins" title="How do I update brewcode plugins?">

<Callout type="tip" title="Recommended: use the skill">
  Run the [`/brewtools:plugin-update`](/brewtools/skills/plugin-update/) skill inside any Claude Code session. It runs the full update chain automatically, reports versions, and prompts you to reload.
</Callout>

If the skill is unavailable (very old install, plugin not yet installed, or Claude refuses to invoke it), paste the prompt below directly into the chat — Claude Code will execute every command for you:

<InstallPrompt plugin="all" mode="update" />

After all commands succeed, run `/reload-plugins` inside your Claude Code session.
If `/reload-plugins` is unavailable, type `exit` and run `claude` again.

</Spoiler>

<Spoiler id="install-too-old" title="My install is too old — the skill isn't available">

If [`/brewtools:plugin-update`](/brewtools/skills/plugin-update/) is missing (very old or partial install), paste the update prompt from [How do I update brewcode plugins?](#update-plugins). It runs the marketplace update and every plugin update, no skill required. Afterwards the skill is available for all future updates.

</Spoiler>

<Spoiler id="claude-refuses" title="Claude refuses to run the update commands">

Paste the update prompt from [How do I update brewcode plugins?](#update-plugins) into the chat. Its coercive phrasing is intentional: it stops Claude from summarizing or skipping steps.

Once an update has succeeded, switch to [`/brewtools:plugin-update`](/brewtools/skills/plugin-update/); it handles refusals internally.

</Spoiler>

<Spoiler id="which-plugins" title="Which plugins are in the suite?">

| Plugin | Purpose | Install command |
|--------|---------|----------------|
| **brewcode** | Convention setup, rules, teams, deep review, semantic search: 9 skills, 6 agents, 2 registered hooks | `claude plugin install brewcode@claude-brewcode` |
| **brewdoc** | Documentation tools: docsync-setup, memory-sync-setup, my-claude, PDF, publishing — 5 skills, 0 agents, 0 hooks | `claude plugin install brewdoc@claude-brewcode` |
| **brewtools** | Text utilities, [SSH](/brewtools/skills/ssh/), [deploy](/brewtools/skills/deploy/), [plugin-update](/brewtools/skills/plugin-update/), manager mode, hook layer: 13 skills, 3 agents, 1 registered hook | `claude plugin install brewtools@claude-brewcode` |
| **brewui** | UI/visual/creative tools (placeholder, empty): 0 skills | `claude plugin install brewui@claude-brewcode` |
| [**brewmod-placeholders**](/mods/placeholders/) | Mod: expands `++` tokens such as `++r` into instruction blocks | `claude plugin install brewmod-placeholders@claude-brewcode` |
| [**brewmod-plan-effort**](/mods/plan-effort/) | Mod: raises main-loop effort while Claude plans | `claude plugin install brewmod-plan-effort@claude-brewcode` |

All six install from the same `claude-brewcode` marketplace on GitHub. The four plugins total 27 skills, 9 agents and 3 registered plugin hooks; optional setup-installed hooks are separate. Mods are covered in [Brewcode mods](/mods/overview/).

</Spoiler>

<Spoiler id="brewcode-mods" title="What are brewcode mods?">

Mods are plugins that change how Claude Code itself behaves, through the hooks module API. There are two: `brewmod-placeholders` expands tokens such as `++r` into instruction blocks and is the only provider of the codewords `++m`, `++a`, `++r`, `++rr` and `+++`, and `brewmod-plan-effort` raises the effort of the main loop while Claude plans.

<Callout type="warning" title="Update Claude Code first">
  The mods need Claude Code 2.1.301 or newer. Check with `claude --version`; if it is lower, run `claude update`.
</Callout>

They are separate from the four suite plugins and install individually (`claude plugin install brewmod-placeholders@claude-brewcode`). [`/brewtools:plugin-update`](/brewtools/skills/plugin-update/) updates them once installed. Details: [Brewcode mods](/mods/overview/).

</Spoiler>

<Spoiler id="setup-suffix" title="Why do some skills end in -setup?">

A `-setup` suffix marks a skill that installs a mechanism into the project — agents, hooks, a generated skill, a board. After it runs you use the installed thing, not the skill. Skills without the suffix are recurring tools: running them repeatedly is the intended usage.

There are eleven `-setup` skills. All share one mode vocabulary, `status | install | upgrade | enable | disable | uninstall | purge`; skill-specific verbs come after it. Use explicit modes: convention-setup defaults to install, semble-setup and manager-setup to status. Enable and disable work through a live config flag (semble, agent-deadline, agent-return, agent-router, manager, docsync) or entry-file parking, renaming the discovery file to `<name>.disabled` (teams, superreview, task-board, convention, memory-sync).

<Callout type="warning" title="Run them one at a time">
  Each setup is an interactive generator: it fans out subagents, analyses the repo and asks you real questions. Two in one session degrade each other. Start with [`/brewcode:setup-status`](/brewcode/skills/setup-status/) and work its list, one setup per fresh session — full details on the [Full Setup](/full-setup/) page.
</Callout>

</Spoiler>

<Spoiler id="auto-invoke" title="Why doesn't Claude run these skills on its own?">

By design. 24 of the 27 skills are user-invoked only: they carry `user-invocable: true` and `disable-model-invocation: true`. The model never sees their descriptions and never auto-activates one; they run only when **you** type `/plugin:skill`.

Three skills are the exception (`disable-model-invocation: false`): `/brewdoc:publish`, `/brewtools:text-optimize` and `/brewtools:text-human`. Claude can run them mid-task: publishing returns a shareable URL, and the text skills are leaf edits on files you name. Other suite skills also call `text-optimize` through `Skill`.

The other 24 keep installation and scope decisions with you. The eleven `-setup` skills write real files into your repo, and recurring tools such as `rules`, `e2e`, `secrets-scan`, `deploy` and `ssh` run when and where you choose.

So "can you sync my docs?" will not trigger `/brewdoc:docsync-setup`; type the command. "Publish this" or "humanize this README" can trigger the three exceptions. Tab completion after `/` lists everything installed.

</Spoiler>

<Spoiler id="restart-after-update" title="Do I need to restart after updating?">

Yes. Plugin changes only take effect after a reload.

<Steps>
  <li class="step step-primary">
    <div>
      <strong>Preferred: reload in session</strong>
      <p>Run <code>/reload-plugins</code> inside your active Claude Code session. This applies updates without closing the terminal.</p>
    </div>
  </li>
  <li class="step step-secondary">
    <div>
      <strong>Fallback: restart the CLI</strong>
      <p>Type <code>exit</code> to close the session, then run <code>claude</code> to start a new one. All updates will be picked up automatically.</p>
    </div>
  </li>
</Steps>

</Spoiler>

<Spoiler id="where-cached" title="Where are plugins cached?">

Plugins are stored locally after installation:

```
~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/
```

For example `~/.claude/plugins/cache/claude-brewcode/brewcode/5.0.0/`. Marketplace metadata lives in `~/.claude/plugins/marketplaces/`.

</Spoiler>

<Spoiler id="check-version" title="How do I check my installed version?">

Run [`/brewtools:plugin-update`](/brewtools/skills/plugin-update/) in a session: it reports installed and latest versions per plugin and offers the update.

<Callout type="note" title="CLI version check (CC 2.1.163+)">
  Run `claude plugin list` (`--json` for machine-readable output). Inside an active Claude session, prefix with `unset CLAUDECODE &&` to avoid the env-var conflict. Older CC lacks the command: use the cache path above or [`/brewtools:plugin-update`](/brewtools/skills/plugin-update/).
</Callout>

</Spoiler>
