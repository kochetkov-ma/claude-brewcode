## Quick reference

| Field | Value |
|-------|-------|
| Type | Claude Code mod (hooks module, no skills or agents) |
| Plugin | `brewmod-plan-effort` |
| Requires | Claude Code 2.1.287+, and `node` on the `PATH` (runs the bundled command hook `hooks/mode.mjs`) |
| Raises | Main loop effort in plan mode, to `planEffort` (default `xhigh`) |
| Never touches | The session `/effort` setting, subagent effort |
| Options | `planEffort`, `statusLine` (both optional, set in `/config`) |
| Status line | `plan: <level>` while the raise is active |
| Works on | Team organizations (Enterprise not run): a bundled command hook reads the mode where Claude Code bypasses a mod's `classic.*` hooks |
| Verified on | Terminal UI, Claude Code 2.1.300: Team-org and Max profiles, `--plugin-dir` and installed copies (Enterprise not run) |

## What it does

The mod raises the effort of the main loop while Claude Code is in plan mode and leaves every other mode at your session effort, for example `high`. No `/effort xhigh` before planning and no `/effort high` after it.

The raise is applied to each model request on its way out, so nothing stays behind if you forget to switch back. Subagents keep their own effort.

The mode comes from a bundled command hook, so the mod also works on Team and Enterprise organizations, where Claude Code's builtin security layer bypasses the `classic.*` hooks of a user-installed mod. Verified live on Claude Code 2.1.300 on a Team-org profile and a Max profile, each with a `--plugin-dir` copy and with a copy installed from a git marketplace. Enterprise orgs were not run.

## When to use

| Scenario | What happens |
|----------|--------------|
| Session on `high`, you press `Shift+Tab` into plan mode | Plan-mode requests run at `xhigh`, no `/effort` change needed |
| You approve the plan and Claude starts editing | The next request is back at your session effort |
| You reject the plan | Effort stays raised, because Claude is still in plan mode |
| Session already on `max` | Nothing changes |
| You want a different plan-mode level | Set `planEffort` in `/config` |

## Example

With the session on `high`:

1. Press `Shift+Tab` until plan mode is on.
2. Send a prompt. The status area shows `⚠ brewmod-plan-effort: plan: xhigh` while Claude plans.
3. Approve the plan. The status line clears and the next request runs at `high`.

The native footer keeps showing your session effort (`high`) during the raised requests. The status line is the only indicator of the raise.

## Configuration

Open `/config` and change the plugin options. Both are optional.

| Option | Type | Default | Values | Effect |
|--------|------|---------|--------|--------|
| `planEffort` | string | `xhigh` | `medium`, `high`, `xhigh`, `max` | Effort for the main loop in plan mode |
| `statusLine` | boolean | `true` | `true`, `false` | Show a status line while plan mode raises the effort |

With the session on `high` and `planEffort` set to `max`, plan mode runs at `max`.

## How it works

<Steps>
  <li><div><strong>Record the permission mode</strong><p>The bundled command hook <code>hooks/mode.mjs</code> runs on <code>UserPromptSubmit</code> and <code>PostToolBatch</code>. It writes the main loop permission mode to <code>.state/mode-&lt;session_id&gt;.json</code> in the plugin root. Payloads with an <code>agent_id</code> are ignored, and state files older than 7 days are pruned.</p></div></li>
  <li><div><strong>Raise effort per request</strong><p>The <code>turn.step</code> event fires before every model request. The module reads the state file for the current session. In plan mode it rewrites <code>effort</code> up to <code>planEffort</code>. Ranks run low, medium, high, xhigh, max. An equal or higher effort, a numeric effort, and an absent effort pass through untouched.</p></div></li>
  <li><div><strong>Show the status line</strong><p>While a request is raised, the mod pins the status text <code>plan: &lt;level&gt;</code>. Claude Code renders it with the plugin name, for example <code>⚠ brewmod-plan-effort: plan: xhigh</code>. The line clears when a main request needs no raise.</p></div></li>
  <li><div><strong>Leave nothing behind</strong><p>The rewrite covers one request, so leaving plan mode needs no cleanup. A missing or unreadable state file counts as not in plan mode. The command hook never blocks a prompt or a tool batch, and the engine skips a failing module hook.</p></div></li>
</Steps>

## Verified

### Current path (command hook)

Measured on Claude Code 2.1.300 (`claude -p --model sonnet`) with the bundled command hook `hooks/mode.mjs`. Source: count of `"effort":"xhigh"` in the session transcript. Each row was run on a `--plugin-dir` copy and on a copy installed from a git marketplace.

| Profile | Mode | `xhigh` requests in the transcript |
|---------|------|------------------------------------|
| Team org | plan | 4 |
| Team org | default | 0 (session level) |
| Max | plan | 4 |
| Max | default | 0 (session level) |
| Installed copy, Team org and Max | plan / default | 4 / 0, same as above |

Enterprise orgs were not run.

### Earlier in-module detection (same effort rewrite)

Measured during development on Claude Code 2.1.300 (Opus 5.5, session effort `high`) with the in-module mode detection that preceded the command hook; the effort rewrite is the same as in this release. Source: `output_config.effort` of each request in the session JSONL.

| Check | Result |
|-------|--------|
| Plan-mode main requests | `xhigh` |
| Default-mode main requests | `high` |
| Explore subagent in plan mode | `high` |
| Approve `ExitPlanMode` | next request `high` |
| Reject `ExitPlanMode` | stays `xhigh` |
| Prompt cache, 3 plan enter/exit pairs in one ~64k-token session | 0 extra cache misses against a control run without the mod, +58 cache-write tokens over 6 mode flips |

Scope: the cache run used requests seconds apart on one model, so cache expiry between slow requests is not covered. Unit tests in `tests/plan-effort.test.ts` (not live runs) cover `planEffort` set to `high` or `max`, an unknown value that counts as unset so the default `xhigh` applies, and `statusLine: false`.

## Limitations

<Callout type="warning" title="Shift+Tab fires no event of its own">
  The mod learns the new mode at the next prompt or tool batch, so a mode switch takes effect then and the status line stays on screen until then. A plan-mode visit that starts and ends between two of those checkpoints is not seen.
</Callout>
