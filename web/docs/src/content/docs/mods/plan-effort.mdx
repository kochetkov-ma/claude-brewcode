## Use it

| You do | You get |
|--------|---------|
| `Shift+Tab` twice from the default mode (`manual mode on` → `accept edits on` → `plan mode on`), or `/plan` | Requests run at `xhigh` from the next prompt; the toast `plan mode: effort xhigh · /plan-effort to change` shows once per plan visit |
| Approve the plan | The next request is back at your session effort, nothing to undo |
| `/plan-effort max` | Plan-mode level set to `max`, same as the `planEffort` option in `/config` |

## Commands

| Command | Result |
|---------|--------|
| `/plan-effort` (also `status`, `help`) | Status block (`plan effort`, `session`, `mode now`) plus usage |
| `/plan-effort <medium\|high\|xhigh\|max>` | Sets `planEffort` and prints `plan effort: <old> -> <new>`; an unknown word prints `unknown '<arg>'` |

`/config` has one option, `planEffort` (default `xhigh`). In `claude -p` there is no `/config` row, so the command asks you to use `/config` interactively.

<Callout type="note" title="Good to know">
  - Your session `/effort` setting is never written, and subagents keep their own effort.
  - The mod only raises: a session already at or above `planEffort` stays as it is.
  - Rejecting a plan keeps the raise, because Claude is still in plan mode.
</Callout>

<Spoiler title="Technical details" id="technical-details" meta="how it works, verification">

**How it works.** The bundled command hook `hooks/mode.mjs` runs on `UserPromptSubmit` and `PostToolBatch` and writes the main loop permission mode to `.state/mode-<session_id>.json` in the plugin root (subagent payloads are ignored, files older than 7 days are pruned). The `turn.step` event fires before every model request; in plan mode the module raises `effort` to `planEffort`. Ranks run low, medium, high, xhigh, max; equal, higher, numeric and absent efforts pass through. The rewrite covers one request, so leaving plan mode needs no cleanup.

**Team organizations.** Claude Code's builtin security layer bypasses the `classic.*` hooks of a user-installed mod, while a bundled command hook still runs. That is why the mode comes from `mode.mjs`. Enterprise organizations were not run.

**Failure mode.** A missing or unreadable state file counts as not in plan mode; no hook blocks a prompt or a tool batch.

<Spoiler title="Verified" id="verified" meta="Claude Code 2.1.300">

Current path (command hook), `claude -p --model sonnet`. Source: count of `"effort":"xhigh"` in the session transcript, run on a `--plugin-dir` copy and on a copy installed from a git marketplace.

| Profile | Mode | `xhigh` requests |
|---------|------|------------------|
| Team org | plan | 4 |
| Team org | default | 0 (session level) |
| Max | plan | 4 |
| Max | default | 0 (session level) |

Subagent, reject, approve and Team-org checks, same version, session effort `high`, effort read per request from the session transcript:

| Check | Profile | Measured |
|-------|---------|----------|
| Explore subagent in plan mode | Max | subagent request at `high` while the main loop ran `xhigh` |
| Reject the plan at ExitPlanMode | Max | next main request still `xhigh` |
| Approve the plan | Max | next main requests back at `high` |
| `/plan-effort max`, then plan mode | Team org | plan-mode main requests at `max`, toast shown |

Prompt cache, measured on the earlier detection path (same effort rewrite): 3 plan enter/exit pairs in one ~64k-token session gave 0 extra cache misses over 6 mode flips against a control run without the mod, and +58 cache-write tokens. The run used requests seconds apart on one model, so cache expiry between slow requests is not covered. The `/plan-effort` command and the toast were checked live on 2.1.300; unit tests cover `planEffort` set to `high` or `max` and an unknown value that counts as unset.

</Spoiler>

<Spoiler title="Limitations" id="limitations">

A plan-mode visit that starts and ends between two prompt or tool-batch checkpoints is not seen. The native footer keeps showing the session effort during raised requests; the toast is the only indicator.

</Spoiler>
