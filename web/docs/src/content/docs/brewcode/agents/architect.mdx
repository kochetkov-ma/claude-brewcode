# Architect

<Callout type="caution">
**The architect agent never writes code.** Write, Edit, and NotebookEdit are disallowed — it can only read, grep, search, and run read-only bash commands. If you need implementation, hand off to the `developer` agent after the architect produces its recommendations.
</Callout>

<Callout type="tip">
**Trigger with natural language.** Phrases like "review the architecture", "design this service", "what are the scaling limits here", or "suggest a pattern for X" all invoke the architect automatically. No slash command needed.
</Callout>

## Quick reference

| Field | Value |
|-------|-------|
| Trigger | "review architecture", "design service", "scaling" |
| Model | `inherit` — runs on the session's model |
| Tools | Read, Glob, Grep, Bash, WebFetch, WebSearch |
| Disallowed | Write, Edit, NotebookEdit |

## Scope guard

The architect sizes the task before starting. One bounded unit = one deliverable, roughly 5 files, roughly 10 steps.

| Situation | What the agent does |
|-----------|---------------------|
| Brief fits one bounded unit | Starts immediately |
| Brief exceeds ~5 files / ~10 steps, or bundles several independent deliverables | Stops before starting, returns a split proposal: 2-N bounded subtasks, each with scope and a suggested owner |
| Scope grows mid-flight | Stops at the next clean boundary, reports done / remaining / how to split |
| Brief is missing GOAL, SCOPE, CONTEXT, CONSUMER or acceptance | States the assumption explicitly in the report, or asks once — never invents scope |

"Review the architecture of the whole repo" is exactly the shape that gets refused. Ask for one module, one service, or one boundary instead.

<Callout type="tip">
**Got a split proposal instead of an analysis?** That is the guard working. Pick one subtask and re-send it, or spawn the subtasks as parallel agents in a single message.
</Callout>

## When to use

- **Design review** — assess one existing module, service, or boundary before a major change
- **Pattern selection** — pick an approach that fits the patterns already established in your codebase
- **Trade-off analysis** — document the gains and costs of a decision before committing
- **Scaling strategy** — identify bottlenecks and the quality dimensions they threaten
- **Pre-implementation** — set boundaries and contracts before handing off to `developer`

## Examples

```
"review the architecture of the payment module"
"design a service for async order processing"
"scaling strategy for high-traffic checkout"
```

The agent reads every `.claude/rules/` file and `CLAUDE.md` first, then searches `.claude/` and `docs/` for existing architecture decisions before forming an opinion — so recommendations follow your conventions, not a textbook.

## Flow

<Steps>
  <li>
    <div>
      <strong>Pre-analysis</strong>
      <p>Reads all rules files ({'`.claude/rules/*-best-practice.md`'}, {'`*-avoid.md`'}), checks <code>CLAUDE.md</code> for stack and conventions, searches <code>.claude/</code> and <code>docs/</code> for existing architecture decisions.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Discovery</strong>
      <p>Greps for similar functionality, patterns, and boundaries, then uses Glob for config and schema files. Runs <code>git log</code> via Bash to understand change history.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Reuse check</strong>
      <p>Explicitly checks for existing utilities, base classes, and established patterns before recommending new abstractions. Prefers battle-tested libraries (JDK → Apache Commons → Guava) over custom code.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Assessment</strong>
      <p>Evaluates six quality dimensions — performance, scalability, reliability, maintainability, security, testability — and names the trade-off behind every finding. It reads your project's own rules and conventions rather than applying a generic architecture checklist.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Recommendations</strong>
      <p>Produces a structured report: components table, findings ranked by severity (H/M/L), recommendations with effort estimate (S/M/L) and explicit trade-offs. Ends with a concrete next action.</p>
    </div>
  </li>
</Steps>

<details>
<summary>Internals</summary>

**Analysis workflow:** Scope → Discover → Assess → Identify → Recommend → Prioritize

**Output format:**
```markdown
## Architecture Analysis: [Component]

### Context
**Scope:** [analyzed] | **Constraints:** [limits]

| Component | Pattern | Quality | Issues |
|-----------|---------|---------|--------|
| [Name] | [Style] | ⚠️/✅/❌ | [Brief] |

| # | Finding | Severity | Impact |
|---|---------|----------|--------|
| 1 | [Issue] | H/M/L | [Effect] |

| # | Recommendation | Effort | Benefit | Trade-off |
|---|----------------|--------|---------|-----------|
| 1 | [Action] | S/M/L | [Gain] | [Cost] |

**Next:** [action]
```

**Scope boundaries:**

| In scope | Out of scope |
|----------|--------------|
| Architecture analysis | Implementation (→ developer) |
| Pattern recommendations | Tests (→ tester) |
| Trade-off evaluation | Code review (→ reviewer) |
| Scaling strategies | Deployment execution |

**Tool order:** Grep/Glob/Read for patterns, boundaries, and structure, Bash for `git log` and dependency graphs, WebSearch for external research.

</details>
