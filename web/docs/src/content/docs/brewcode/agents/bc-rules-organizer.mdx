# Rules Organizer

<Callout type="note">
**Internal agent — no direct or automatic use.** `bc-rules-organizer` is spawned only by [`/brewcode:rules`](/brewcode/skills/rules/), never by you directly and never auto-selected by Claude for an unrelated prompt. It exists as a page here because it ships as one of brewcode's 5 agents and deserves the same reference treatment as the other 4.
</Callout>

<Callout type="note" title="What's new in 6.2.0">
The agent definition was restructured (role → return contract → scope → procedure → tables) and one long-standing loading claim got corrected:
- `paths:`-scoped rules load lazily, not at session start — see Loading (verified 2.1.269) below.
- New rule files scaffold via `rules.sh create`/`create-specialized` — see Workflow step 4 below.
- The rule-file frontmatter contract is now explicit: beyond `paths:`, every file needs `description`, `doc_type`, `version`, `generated_by`, `last_updated`.
- New **Scope Fit** guardrail — find the closest existing rule file before writing a new one; keep changes additive, never a wholesale replacement.
- Sections renamed for density (Table Formats → Table formats, Frontmatter Reference → Frontmatter, Checkpointing + Return Contract → Return) — same content, tighter headings.
</Callout>

## Quick reference

| Field | Value |
|-------|-------|
| Model | `haiku` — pinned, cheap file reorganization |
| Tools | Read, Write, Edit, Glob, Grep, Bash, Agent |
| Write access | `.claude/rules/` directory only |
| `maxTurns` | 60 — anti-loop stop, not a budget |
| Invocation | Spawned by `/brewcode:rules` via the Task tool — not a slash command, no manual trigger |

## Scope guard

Rules Organizer never sizes or splits a brief itself — `/brewcode:rules` already batches and confirms the rule set before the single spawn, so scope is fixed to what it was handed.

| Situation | What the agent does |
|-----------|---------------------|
| Brief matches the accepted rule batch | Writes only inside `.claude/rules/` — every other path is off-limits |
| Request reaches beyond rule organization | Reports it back instead of expanding scope |
| Brief omits CONTEXT (what the skill already did) or CONSUMER (who reads the rules next) | States the assumption in the report, or asks once — never invents scope |
| `maxTurns: 60` is hit mid-run | Run aborts; rules already written survive, next run resumes from the last file logged in the report |
| Before writing a new rule file (Scope Fit) | Finds the closest well-built existing rule file in `.claude/rules/*.md` first and takes its principles — additive, never a wholesale replacement; after finishing, one pass to cut files/config/indirection if the result can be simpler |

## What it does

Rules Organizer takes rules extracted from a source file (CLAUDE.md, docs, code) and turns them into `.claude/rules/*.md` files with correct `paths:` frontmatter — one file per logical scope, deduplicated against everything already there, formatted as numbered tables instead of prose.

It owns two authoritative table formats (`| # | Avoid | Instead | Why |` and `| # | Practice | Context | Source |`), a 3-check dedup protocol that catches near-duplicates and avoid/best-practice antonym pairs, and a hard 20-row-per-file ceiling that forces a split into `{prefix}-avoid.md` / `{prefix}-best-practice.md` once a file grows past it.

## Example

```text
/brewcode:rules "extract logging and SQL conventions from CLAUDE.md"
```

The skill reads the source, proposes rule candidates, asks you to accept/reject in batches, then spawns `bc-rules-organizer` once with the accepted set. Expected result: `.claude/rules/logging.md` and `.claude/rules/sql-best-practice.md` created or updated, each with `paths:` frontmatter, numbered tables, and a report listing files created/updated plus a rule count.

## Workflow

<Steps>
  <li>
    <div>
      <strong>Analysis</strong>
      <p>Reads the source file completely, identifies rule categories, maps each to a path pattern (or auto-detects from project structure), checks existing rules first.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Extraction</strong>
      <p>Groups rules by logical scope (component, API, test, build, module) and classifies each as anti-pattern (avoid) or best practice.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Optimization and dedup</strong>
      <p>Converts prose to tables, applies abbreviations, adds lazy links for detail. Runs the 3-Check Dedup Protocol: within-file similarity, cross-file avoid/best-practice antonym pairs, and a CLAUDE.md duplicate check — anything already in CLAUDE.md is skipped, never re-added.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>File creation</strong>
      <p>New files scaffold automatically; editing an existing file is manual. Behavior differs by action:</p>

      | Action | Behavior |
      |--------|----------|
      | Scaffold | <code>rules.sh create</code> (global) or <code>rules.sh create-specialized {'<prefix>'} '{'<paths>'}'</code> (scoped) — stamps <code>doc_type</code>/<code>version</code>/<code>generated_by</code>/<code>last_updated</code> |
      | Edit existing file | Only refreshes <code>last_updated</code> and <code>version</code> by hand |
      | Naming | Global <code>avoid.md</code>/<code>best-practice.md</code> carry no <code>paths:</code>; every <code>{'{prefix}'}-avoid.md</code> style file needs one |
      | Row cap | Max 20 rows per table; splits into a new specialized file once exceeded |
      | Validate | <code>rules.sh validate</code> runs after every write and must pass before finishing |
    </div>
  </li>
  <li>
    <div>
      <strong>Checkpoint per file</strong>
      <p>Appends each finished file (path + what changed) to <code>.claude/reports/YYYYMMDD-HHMMSS_rules-organizer/report.md</code> right after writing it — not held to the end. If <code>maxTurns</code> is hit, written rules survive; the run resumes from the last file listed in that report.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Optimize and report</strong>
      <p>Spawns <code>brewtools:text-optimizer</code> once per created/updated file, all in one message — skipped with a note if <code>brewtools</code> is not installed, never a blocker. Returns a final report: files created/updated table, rule counts, and next-step checklist.</p>
    </div>
  </li>
</Steps>

<details>
<summary>Technical details — frontmatter, dedup protocol, file naming</summary>

### Rule-file frontmatter contract

`paths:` is the only field Claude Code itself reads for scoping — source: [code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory.md#path-specific-rules) (`globs`, `alwaysApply`, `description`-as-scoping are not real fields). On top of that, `rules.sh validate` requires five more keys on every rule file the agent writes: `description`, `doc_type`, `version`, `generated_by`, `last_updated`.

```yaml
---
paths:
  - "src/components/**/*.tsx"
  - "!src/components/**/*.test.tsx"
description: "..."
doc_type: llm
version: "6.1.4"
generated_by: "brewcode:rules"
last_updated: "2026-09-12"
---
```

Patterns must be quoted (`"**/*.tsx"`, not bare) and given as an array, never a bare string; `doc_type` is the one unquoted value (`doc_type: llm` exactly).

### Loading (verified 2.1.269)

| Frontmatter | Behavior |
|-------------|----------|
| No `paths` | Loads at session start, same priority as project CLAUDE.md |
| With `paths` | Loads lazily — only when Claude reads a file matching the glob, not on every tool use |

This reverses bug [#16299](https://github.com/anthropics/claude-code/issues/16299)'s old claim that all rules load at session start regardless of `paths:` — no longer reproducible. Because scoping now genuinely delays loading, a rule that must fire before any file is in context stays unscoped:

| Rule kind | `paths:`? |
|-----------|-----------|
| Language/dir conventions (naming, test layout, SQL style) | yes |
| Tool-choice and search policy (lsp-first, semble-first) | no |
| Global anti-patterns | no |

### 3-Check Dedup Protocol

| Check | Scope | Action |
|-------|-------|--------|
| 1. Within-file | Same target file | >70% similarity skip; 40-70% merge |
| 2. Cross-file antonym | Paired avoid/best-practice file | Same concept as opposite — keep the avoid entry, delete the best-practice one |
| 3. CLAUDE.md duplicate | Project CLAUDE.md | Already documented there — skip entirely, `"CLAUDE.md"` is a forbidden Source value |

### File naming

| Pattern | Example | Content |
|---------|---------|---------|
| Global | `avoid.md`, `best-practice.md` | No `paths:` |
| Path-scoped pair | `{'{prefix}'}-avoid.md`, `{'{prefix}'}-best-practice.md` | Common prefixes: test, sql, api, security, kotlin, java, react |
| Domain-specific | `bq-core.md`, `logging.md` | Mixed avoid + best-practice tables under one `paths:` scope |

### Version stamping (v5.1.0+)

Its frontmatter `version`, `generated_by`, and `last_updated` are rewritten at release, never edited by hand.

</details>

## Return Contract

Verdict first, `<=30 lines`, `path:line`. No rule-file bodies, no pasted tables, no extraction notes, no preamble. Returns one row per file (path, matched <code>paths:</code>, change) plus totals: new/updated counts, rule counts, dedup skipped/merged, and whether text-optimizer ran. Dedup ledger, per-rule rationale, and source excerpts go to the same <code>.claude/reports/&lt;YYYYMMDD-HHMMSS&gt;_rules-organizer/</code> checkpoint file — only the path comes back.

[`/brewtools:agent-return-setup`](/brewtools/skills/agent-return-setup/) enforces this at ~1000 / ~2500 est-tokens when installed; the contract itself ships unconditionally.
