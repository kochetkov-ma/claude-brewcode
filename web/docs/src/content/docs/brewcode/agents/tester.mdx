# Tester

<Callout type="caution">
**Flaky tests, regressions, and mysterious CI failures cost hours of developer time.** When tests start failing after a refactor, the root cause is rarely obvious — stack traces mislead, shared state hides bugs, and sleep-based waits mask timing issues. The tester agent exists to handle exactly this class of problem without pulling the developer away from production code.
</Callout>

<Callout type="tip">
**Tester runs tests, diagnoses failures, and fixes test-level issues autonomously.** Production bugs are routed to [developer](/brewcode/agents/developer/) with a precise report — test-level issues and flakiness are fixed in place. Trigger with: "run tests", "tests failing", "flaky test".
</Callout>

## Quick reference

| Field | Value |
|-------|-------|
| Model | sonnet |
| Tools | Read, Write, Edit, Glob, Grep, Bash, Task |
| Triggers | "run tests", "tests failing", "flaky test" |
| Scope YES | Run tests, analyze failures, debug flaky, configure runs, report issues, minor test fixes |
| Scope NO | Fix production code (→ developer), substantial test rewrites (→ developer) |

## Scope guard

Tester sizes the task before starting. One bounded unit = one deliverable, roughly 5 files, roughly 10 steps.

| Situation | What the agent does |
|-----------|---------------------|
| Brief fits one bounded unit | Starts immediately |
| Brief exceeds ~5 files / ~10 steps, or bundles several independent deliverables | Stops before starting, returns a split proposal: 2-N bounded subtasks, each with scope and a suggested owner |
| Scope grows mid-flight | Stops at the next clean boundary, reports done / remaining / how to split |
| Brief is missing GOAL, SCOPE, CONTEXT, CONSUMER or acceptance | States the assumption explicitly in the report, or asks once — never invents scope |

"Fix all 60 failing tests in the suite" gets a split proposal. Send one module or one failure class at a time.

<Callout type="tip">
**Got a split proposal instead of a test report?** That is the guard working. Pick one subtask and re-send it, or spawn the subtasks as parallel testers in a single message.
</Callout>

## When to use

- **Post-refactor validation** — tests broke after a code change, need failure triage before developer continues
- **Flaky test elimination** — tests that pass sometimes and fail other times, timing or state issues
- **CI failure investigation** — build is red, need a structured failure report with root cause
- **Coverage gaps** — need to understand what's covered and what's missing before a release
- **Regression and infrastructure failures** — tester resolves these directly instead of blocking developer

## Flow

<Steps>
  <li>
    <div>
      <strong>Pre-analysis</strong>
      <p>Reads all rules (<code>.claude/rules/\*-best-practice.md</code>, <code>.claude/rules/\*-avoid.md</code>) and <code>CLAUDE.md</code> for test commands, frameworks, and coverage requirements. Analyzes existing test patterns before touching anything.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Execute and capture</strong>
      <p>Runs the test command taken from the project config. Captures full output — pass/fail counts, stack traces, timing. No guessing at commands; uses the project-defined entrypoint.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Analyze failures</strong>
      <p>Reads stack traces bottom-up, compares expected vs actual values. Categorizes each failure: TEST BUG (fix here), PRODUCTION BUG (route to developer), ENVIRONMENT issue, or FLAKY (fix here).</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Fix in scope</strong>
      <p>Applies minor test-level fixes directly — flaky timing, shared state, broken assertions. Substantial rewrites are handed to developer instead.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Report</strong>
      <p>Produces a structured report with scope, command, duration, summary counts, failure details with root cause and fix suggestions, flaky list, coverage numbers, and next steps. Production bugs go to developer with a precise reproduction path.</p>
    </div>
  </li>
</Steps>

<details>
<summary>Internals</summary>

**Output format**

```
=== TEST EXECUTION REPORT ===
Scope: [level] | Command: [cmd] | Duration: [time]
SUMMARY: ✅ Passed: X | ❌ Failed: Y | Skipped: Z

FAILURES (→ DEVELOPER):
1. [Test#method] File: [path:line]
   Error: [msg] | Expected: [x] | Actual: [y]
   Root cause: [analysis] | Fix: [suggestion]

FLAKY (I will fix): [list]
COVERAGE: Line [%] | Branch [%]
NEXT: Developer fixes [list] → Re-run
```

**Failure categories**

| Category | Owner |
|----------|-------|
| TEST BUG | Tester fixes it |
| FLAKY | Tester fixes it |
| ENVIRONMENT | Tester reports and, where possible, reconfigures the run |
| PRODUCTION BUG | Routed to [developer](/brewcode/agents/developer/) |

**Scope boundary**

Tester fixes test code and configuration, including minor test fixes. Substantial test rewrites and any change to production code go to developer, with a report including test name, file path, expected vs actual values, and root cause analysis.

Conventions for test structure and assertions come from your project's own `.claude/rules/` files and `CLAUDE.md` — tester reads them before running anything and does not impose a built-in style guide.

</details>
