# Brewcode Overview

<InstallPrompt plugin="brewcode" mode="install" />

Install the entire suite:

<InstallPrompt plugin="all" mode="install" />

Brewcode is a plugin for Claude Code for spec authoring, multi-agent review, and a toolkit of
skills and agents. The name is a nod to brewing: skills (recipes) define what to brew, agents
(brewers) do the work, and hooks (processes) manage prompt-time injection.

## Architecture

Brewcode works as a layer on top of Claude Code through the hook system. The plugin has no external runtime --
all context is managed through built-in Claude Code events.

```
                         Brewcode Plugin
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │   Skills (recipes)            Agents (brewers)           │
  │   ┌──────────────┐          ┌──────────────────┐         │
  │   │ semble-setup │          │ skill/agent/hook  │         │
  │   │ superrev-... │ ──────>  │ creator, bash     │         │
  │   │ e2e, conv... │          │ + project teams   │         │
  │   └──────────────┘          └──────────────────┘         │
  │          │                          │                     │
  │          v                          v                     │
  │   Hooks (processes)           Templates + Knowledge      │
  │   ┌──────────────┐          ┌──────────────────┐         │
  │   │ session-start│          │ rules templates   │         │
  │   │ forced-eval  │ <──────> │ artifacts/        │         │
  │   │ role-recall  │          │                   │         │
  │   │compact-recall│          │                   │         │
  │   └──────────────┘          └──────────────────┘         │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

## Plugin structure

```
brewcode/
├── .claude-plugin/
│   └── plugin.json                    # Plugin manifest
├── hooks/
│   ├── hooks.json                     # 4 hooks (SessionStart x3, UserPromptSubmit)
│   ├── session-start.mjs              # Version-check, plan-symlink, permission tag
│   ├── forced-eval.mjs                # [ROLE] delegate + [SPLIT] bounded units + [BRANCH] default-to-main
│   ├── role-recall.mjs                # SessionStart/compact: re-inject the same [ROLE]/[SPLIT]/[BRANCH]
│   ├── compact-recall.mjs             # SessionStart/compact: re-anchor plan, intent, task graph
│   └── lib/
│       ├── utils.mjs                  # I/O, version cache, configuration
│       └── reminder.mjs               # REMINDER_TEXT, shared by forced-eval.mjs and role-recall.mjs
├── agents/                            # 5 agents
│   ├── skill-creator.md               # Skill creation (inherit)
│   ├── agent-creator.md               # Agent creation (inherit)
│   ├── hook-creator.md                # Hook creation (inherit)
│   ├── bash-expert.md                 # Bash scripts (inherit)
│   └── bc-rules-organizer.md          # Rules organizer (haiku)
├── skills/                            # 9 skills
│   ├── semble-setup/                  # Semantic code search MCP
│   ├── convention-setup/              # Coding, testing and architecture foundation
│   ├── rules/                         # Rule extraction
│   ├── superreview-setup/             # Multi-agent quorum review generator
│   ├── setup-status/                  # Read-only cross-plugin setup dashboard
│   ├── skills/                        # Skill management
│   ├── agents/                        # Agent management
│   ├── teams-setup/                   # Dynamic agent teams
│   └── e2e/                           # E2E testing orchestration
├── modes/
│   └── manager.md                     # Manager-mode system prompt fragment
└── templates/                         # Rule templates
```

## Naming: `-setup` vs bare

<Callout type="tip" title="The suffix tells you how often to run it">
A **`-setup`** skill installs a mechanism — agents, hooks, a rule, a generated skill — that you then use. Run it once and `upgrade` it when needed. Bare-named skills are recurring tools. Every setup answers `status`, `install`, `upgrade`, `enable`, `disable`, `uninstall`, `purge`. A bare invocation normally means status when installed and install when absent. [`semble-setup`](/brewcode/skills/semble-setup/) always defaults to status; [`convention-setup`](/brewcode/skills/convention-setup/) defaults to install and checks status before extraction.
</Callout>

Convention setup establishes coding, testing and architecture patterns after the search foundation
and before teams and review setup. It installs reversible loading guidance; disabling that guidance
keeps the generated documents readable.

## Artifact metadata

v5.1.0 standardizes what every `-setup` skill stamps onto what it installs, across all four
plugins. Version always comes from `.claude-plugin/plugin.json`, never hardcoded and never the
literal `unknown` — a writer that cannot resolve it refuses to write rather than stamp a fake.

| Field | Values | Where |
|-------|--------|-------|
| `doc_type` | `llm` \| `user` \| `skip`, unquoted | `.md` frontmatter only, never JSON |
| `version` | quoted `"X.Y.Z"` | every carrier |
| `generated_by` | quoted `"<plugin>:<skill>"` | every carrier |
| `last_updated` | quoted `"YYYY-MM-DD"` | every carrier except a byte-copied `.mjs`/`.sh`/`.md` — the date would just be the release date and would churn the drift check |

Five carriers, depending on the file type it is stamping:

| Carrier | Applies to |
|---------|-----------|
| JSON top-level keys | JSON artifacts |
| `.md` frontmatter | generated `.md` skills and docs |
| `// brewcode-meta:` one-liner, line 2 | byte-copied `.mjs`/`.sh` |
| header table (`\| Version \|`, `\| Generated by \|`, `\| Last update \|`) | `team.md` |
| `<!-- brewcode-meta: ... -->`, line 1 | byte-copied `.md` |

[`/brewcode:setup-status`](/brewcode/skills/setup-status/) is the
payoff — it reads these stamps back and compares them against the installed plugin version across
all eleven `-setup` skills to report installed, stale or partial. See
[`superreview-setup`](/brewcode/skills/superreview-setup/#version-and-ownership) for one skill's
full version of this contract.

## Components in detail

<Tabs>
  <TabItem label="Skills">
    9 skills (recipes) cover search, review, conventions, and meta-tooling.
    See [Skills](/brewcode/skills/) for details.

    | Group | Skills | Purpose |
    |-------|--------|---------|
    | Search | semble-setup | Semantic code-search MCP install and maintenance |
    | Convention foundation | convention-setup | Coding, testing and architecture documents with reversible loading guidance |
    | Quality | superreview-setup, rules | Multi-agent review and accepted rule extraction |
    | Dynamic | teams-setup | Agent team creation and management |
    | Testing | e2e | E2E testing orchestration with BDD scenarios |
    | Meta | skills, agents | Skill and agent management |
    | Dashboard | setup-status | Read-only: what is installed, stale or missing across all four plugins |
  </TabItem>
  <TabItem label="Agents">
    5 agents (brewers), all specialists. Generic implementation/review roles are generated per project
    into `.claude/agents/` by [/brewcode:teams-setup](/brewcode/skills/teams-setup/) — brewcode no longer ships them.
    See the [Agents](/brewcode/agents/) section for details.

    | Role | Agents | Model |
    |------|--------|-------|
    | Creation | skill-creator, agent-creator, hook-creator | inherit |
    | Scripting | bash-expert | inherit |
    | Internal | bc-rules-organizer | haiku |

    + dynamic project agents created by [`/brewcode:teams-setup`](/brewcode/skills/teams-setup/)

    Creator agents and on-demand references follow official authoring contracts checked through
    Claude Code 2.1.285. They distinguish ordinary agents, conversation forks and skill forks,
    honor current plugin field restrictions, and return unresolved decisions to the main caller.
    Main owns dispatch and review under repository policy; local validation is distinct from live evaluation.
  </TabItem>
  <TabItem label="Hooks">
    4 hooks manage prompt-time injection, session start, and post-compaction recovery.
    See the [Hooks](/brewcode/hooks/) section for details.

    | Event | Hook | Purpose |
    |-------|------|---------|
    | SessionStart | session-start | Initialization, version-check |
    | UserPromptSubmit | forced-eval | Manager-role + split-discipline reminder |
    | SessionStart (compact) | role-recall | Re-inject [ROLE]/[SPLIT]/[BRANCH] after a compaction |
    | SessionStart (compact) | compact-recall | Re-anchor plan, intent and task graph after a compaction |
  </TabItem>
</Tabs>

## Quick start

<Steps>
  <li class="step step-primary">
    <div>
      <strong>See what is already here</strong> <Badge variant="primary" text="/brewcode:setup-status" />
      <p>Read-only. One table of every setup skill across brewcode, brewtools and brewdoc: installed, stale, partial, missing — plus the exact command for each row. Writes nothing.</p>
    </div>
  </li>
  <li class="step step-primary">
    <div>
      <strong>Convention foundation</strong> <Badge variant="primary" text="/brewcode:convention-setup install" />
      <p>After search setup, extract coding, testing and architecture patterns into <code>.claude/convention/</code> and install loading guidance. Do this before teams and review setup.</p>
    </div>
  </li>
  <li class="step step-primary">
    <div>
      <strong>Team install</strong> <Badge variant="secondary" text="/brewcode:teams-setup install" />
      <p>Create project-specific agents that use the convention foundation.</p>
    </div>
  </li>
  <li class="step step-secondary">
    <div>
      <strong>Deep review</strong> <Badge variant="primary" text="/brewcode:superreview-setup install" />
      <p>Generate a project-tailored review skill using project agents, gates and conventions.</p>
    </div>
  </li>
</Steps>

<Callout type="caution" title="One setup per session">
  Every `-setup` skill is an interactive generator: it fans out subagents, analyses the repo and asks you real questions. Two in one session degrade each other — the second answers against the first one's stale analysis. Run them one at a time, ideally in a fresh session each. That is exactly why `setup-status` reports and stops instead of running anything.
</Callout>
