# spec — research and write spec

<Callout type="caution">
**Skipping spec means rewriting later.** Without a specification, parallel agents and reviewers have no shared ground truth — they duplicate work, contradict each other, and miss edge cases. The fix costs more than the spec would have.
</Callout>

<Callout type="tip">
**`-n` / `--noask` for CI and scripts.** Pass the flag to suppress all `AskUserQuestion` calls — spec is generated and reviewed automatically, no human in the loop. Useful when piping requirements from a file or external tool.
</Callout>

## Quick reference

| Field | Value |
|-------|-------|
| Command | `/brewcode:spec` |
| Arguments | `[-n] <description> \| <path-to-requirements>` |
| Flag | `-n`, `--noask` — skip all clarifying questions |
| Model | opus |
| Context | session |
| Tools | Read, Write, Glob, Grep, Bash, Task, AskUserQuestion |

## When to use

- **New feature or task** — turn a description or requirements file into a structured SPEC.md
- **Ambiguous requirements** — clarifying questions surface scope, constraints, and edge cases before research begins
- **Large scope** — the skill detects when requirements span more than 3 independent areas and suggests splitting
- **Automated pipelines** — `--noask` skips interaction; pipe a requirements doc path as the argument

## Examples

```bash
# From a plain description
/brewcode:spec "add JWT refresh token rotation to auth service"

# From an existing requirements file
/brewcode:spec path/to/requirements.md

# No interaction — auto-approve all defaults
/brewcode:spec -n "migrate database layer to async repositories"
```

Expected output after a successful run:

```
# Spec Created

Files Created:
  SPEC: .claude/tasks/20260417_143052_auth_feature_task/SPEC.md
  Task Dir: .claude/tasks/20260417_143052_auth_feature_task/

```

## Flow

<Steps>
  <li>
    <div>
      <strong>Detect a SPEC template (optional)</strong>
      <p>Checks for <code>.claude/tasks/templates/SPEC.md.template</code>. Present, it is used as-is; absent, the skill falls back to its built-in SPEC structure. Either way the run continues — a missing template is not an error.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Parse input and ask clarifying questions</strong>
      <p>Reads <code>$ARGUMENTS</code>: plain text becomes the task description; a path is read as requirements; empty args fall back to <code>.claude/TASK.md</code>. Then (unless <code>--noask</code>) fires up to 3 batches of questions — scope, constraints, edge cases. If requirements span more than 3 independent areas, proposes splitting into separate tasks.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Partition research areas</strong>
      <p>Divides the codebase into 5–10 logical zones: controllers, services, repositories, tests, config, docs, domain-specific paths. Each zone gets an assigned agent type. Team agents from <code>.claude/teams/</code> take priority over plugin agents.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Parallel codebase research</strong>
      <p>Spawns 5–10 subagents in a <em>single message</em> — Plan, developer, tester, reviewer, Explore — each scoped to one research zone. Agents return findings as bullet lists and file:line references, never large code blocks.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Consolidate into SPEC.md</strong>
      <p>Creates the task directory (<code>.claude/tasks/&#123;TIMESTAMP&#125;_&#123;NAME&#125;_task/</code>), merges and deduplicates agent findings, fills all SPEC sections per the detected template or the built-in structure, and writes the file. A research table records which agent covered which area.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Validate findings with user</strong>
      <p>Unless <code>--noask</code>, presents key architectural decisions, risk assessment, and assumptions via <code>AskUserQuestion</code>. User feedback is incorporated into SPEC before the review pass.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Reviewer loop</strong>
      <p>A reviewer agent checks the SPEC for completeness, consistency, feasibility, and risks. All critical and major remarks are fixed and re-reviewed — up to 3 iterations. Remaining remarks after 3 rounds are surfaced to the user.</p>
    </div>
  </li>
</Steps>

## Delegation

<Callout type="caution" title="Why research is partitioned">
  A big task handed to one agent = an agent gone for an hour: you cannot observe it, cannot correct it, and it usually drifts off-target.
</Callout>

One subagent = **ONE bounded unit** — here, ONE research area: roughly 5 files, roughly 10 steps. Splitting the codebase into 5-10 areas *is* that sizing rule applied; all of them are spawned in **ONE message**, never chained.

Every spawn prompt carries six fields. A bare one-line task is never enough:

| Field | Content |
|-------|---------|
| GOAL | the overall task and why it exists — the point beyond the file edit |
| ROLE | what this agent owns; what it must NOT touch |
| SCOPE | exact paths/commands in bounds + explicit out-of-bounds |
| CONTEXT | what is already done, by whom, what runs in parallel — trimmed to what THIS agent needs |
| CONSUMER | who or what uses the result next, and the shape it must fit |
| DONE | acceptance criteria + the exact report shape you want back |

A research agent is therefore told: it is read-only and does not write the SPEC; scope and constraints were settled with you in step 2 and must not be re-opened; the step 2.5 split already fixed the task boundary; N siblings cover the other areas from the partition table. Its CONSUMER line does the real work — step 5 merges and deduplicates the reports and step 7 has a reviewer grade the SPEC, so a finding outside the four required sections is dropped in the merge, and an omitted risk comes back as a reviewer bounce. The same brief lives in `references/SPEC-creation.md`.

<details>
<summary>Phase details — input handling, agent prompt template, output format</summary>

**Input detection (after flag stripping)**

| `$ARGUMENTS` | Action |
|--------------|--------|
| Empty | Read `.claude/TASK.md` — first line = path — derive task dir |
| Plain text | Use as task description |
| File path | Read file contents as task description |

**Naming convention**

- Timestamp: `YYYYMMDD_HHMMSS` (e.g., `20260417_143052`)
- Name slug: lowercase, underscores (e.g., `auth_feature`)
- Task directory: `.claude/tasks/{TIMESTAMP}_{NAME}_task/`

**Agent prompt template (research phase)**

Each parallel subagent receives a prompt in this shape:

```
GOAL: we are writing a SPEC for "{TASK_DESCRIPTION}". Your findings become one section of
      that SPEC; other agents cover the other areas in parallel.
ROLE: you own the {AREA} analysis only. Read-only — do NOT edit code, do NOT write the SPEC.
SCOPE: {FILES_IN_AREA}. Out of bounds: every other area (owned by sibling agents).
CONTEXT: scope and constraints are already settled with the user — do NOT re-open them.
      {N} sibling agents research the other areas in this same message.
CONSUMER: step 5 merges the 5-10 reports into one SPEC.md; step 7 has a reviewer grade it on
      completeness, consistency, feasibility and risks.
DONE: report exactly — findings (bullets), assets (table), risks, recommendations.
      NO large code blocks — use file:line references.
```

**Dynamic agent resolution order**

1. Team agent from `.claude/teams/team.md` matching the domain
2. Project agent from `.claude/agents/`
3. Plugin agent (developer, tester, reviewer, Explore, Plan)

**Reviewer iteration loop**

```
WHILE remarks.critical > 0 OR remarks.major > 0:
  Fix all critical/major remarks in SPEC.md
  Re-run reviewer agent
MAX 3 iterations — then surface remaining remarks via AskUserQuestion
```

**Template source:** a project `.claude/tasks/templates/SPEC.md.template` when one exists; otherwise the skill's built-in SPEC structure.

</details>
