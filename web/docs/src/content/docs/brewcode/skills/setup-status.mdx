# Setup Status

<Badge text="sonnet" /> <Badge text="read-only probes" /> <Badge text="11 setups" />

<SourceLink path="brewcode/skills/setup-status/README.md" anchor="setup-status" />

Inspect a repository or check copied artifacts after a plugin update. The skill
reports each setup as current, disabled, missing, partial, stale or modified and prints the exact
next command. It runs no setup itself and spawns no agents.

## Quick reference

| Field | Value |
|-------|-------|
| Command | `/brewcode:setup-status` |
| Input | Free-text prompt; optional plugin or skill filter |
| Covers | Eleven setups across brewcode, brewtools, and brewdoc |
| Writes | No setup artifacts; one optional, explicitly accepted task-tools settings key |

## When to use

| Situation | Command |
|-----------|---------|
| Inspect the whole project | `/brewcode:setup-status` |
| Inspect one plugin | `/brewcode:setup-status brewtools` |
| Inspect conventions and their loading rule | `/brewcode:setup-status convention-setup` |

Filters can sit in a free-text RU/EN prompt; other text gives the full report. Commands stay literal.

## Example

```text
/brewcode:setup-status convention-setup
```

Without conventions, expect a `missing` row pointing to `/brewcode:convention-setup install`.

<Callout type="warning" title="Run setups yourself, one per session">
  Setups are interactive generators. Follow the report's commands separately, in fresh sessions. There is no `--run`, `--fix`, or automatic mode.
</Callout>

## How it works

<Steps>
  <li><div><strong>Resolve plugin roots</strong><p>Find the installed plugins and their versions. A missing plugin gives an `n/a` row; an unresolved version is reported, never guessed.</p></div></li>
  <li><div><strong>Probe artifacts and off-switches</strong><p>Check anchors, secondary files, settings, and parked entries.</p></div></li>
  <li><div><strong>Compare content, ownership, bytes</strong><p>Compare each artifact's content version with its own plugin source, check `generated_by`, and compare copied files byte by byte.</p></div></li>
  <li><div><strong>Print verdicts and the run-list</strong><p>Partial installs come first within a stage, then stale and modified, then missing.</p></div></li>
  <li><div><strong>Check roster and task tools</strong><p>Warn about unknown setups, else print `roster: 11/11 in sync`. Offer the task-tools key merge if no layer sets it.</p></div></li>
</Steps>

Recurring tools have no installed state and stay out of the roster. The run-list follows seven stages, from agent-return and semble through
conventions, teams, consumers, task-board and memory-sync with docsync. The order and install
commands live on [Full Setup](/full-setup/).

## Technical details

<Spoiler id="verdicts" title="Verdicts and off-switches">

Evaluated in this order:

| Verdict | Meaning |
|---------|---------|
| `n/a` | The owning plugin is unavailable |
| `disabled` | The setup's off-switch confirms deliberate disablement |
| `missing` | Anchor and secondary artifacts absent in live and disabled spellings; manager with only `state.json`: `state.json only, wall not installed`, command `install` |
| `partial` | Incomplete install, half-applied toggle, unresolved metadata, or wrong ownership; semble also: hand-edited rule with outdated stamp, or permissions missing everywhere |
| `stale` | Content-version, byte, absence, or wiring signals need refresh; reads `stale (installed X.Y.Z, plugin A.B.C)` when versions differ |
| `modified` | `modified (stamp current, bytes differ)`: a copied file was edited or never re-copied |
| `current` | Required artifacts and checks agree; `current (restamp pending)` when a copied file differs only in its stamp lines (optional `upgrade` restamps) |

Convention checks the loader plus its three generated documents; a parked loader (`convention.md.disabled`) reads `disabled`.

| Setup group | Disabled signal |
|-------------|-----------------|
| teams | Every roster member parked as `.disabled`, except the shared intent-guard and agents owned by another generator (such as task-tracker) |
| superreview, memory-sync | Generated `SKILL.md` parked as `.disabled` |
| task-board | Every deployed machinery entry parked; task data stays |
| convention | Loading rule parked; documents and accepted rules stay |
| semble | State `enabled` is false |
| manager | State `hard` is not `true`, on an installed wall (copied guard or registration) |
| agent-deadline, agent-return | Config `enabled` is not `true`; missing key means off |
| agent-router, docsync | Config `enabled` is false; missing key means on |

Disabled wins over the repair verdicts. A manager `state.json` alone is not a wall, so the row reads `missing`. A disabled row behind the plugin gets `upgrade` (stays disabled) for semble, agent-deadline, agent-router, manager, docsync, agent-return, and convention; teams, superreview, task-board, and memory-sync refuse `upgrade` while parked, so the row gets `enable`, `upgrade`, then `disable`.

</Spoiler>

<Spoiler id="technical-signals" title="Signals, stamps and carriers">

| Signal | Question |
|--------|----------|
| `content_version` | Has this artifact's own tracked content changed? |
| `version` | Which plugin release produced this install? |
| `generated_by` | Did the owning setup write this path? |
| `cmp` comparison | Was a copied asset refreshed, or has its body drifted? |

The content version is compared with the plugin source for that same artifact, so an unrelated release does not make an install stale. The `STAMPS` table in `references/phase2-stamps.md` holds **23 carrier entries: 7 brewcode, 13 brewtools, 3 brewdoc**; counts describe carriers, not setups. Copied-byte checks cover the hooks, rules, guards and references the roster names; semble wiring is checked separately and its root `.sembleignore` is excluded. Hook entries still using absolute paths (releases up to 6.5.0) are the one drift sent to `upgrade`; other stale or missing wiring keeps `install`.

</Spoiler>

<Spoiler id="guards-and-semble" title="Guard configs and the semble rule">

For agent-deadline and agent-return, `GOVERNING` names the config the guard would load and `CLIMB-START` where the search began (payload cwd for agent-deadline, the guard's project root for agent-return; an explicit `CLAUDE_PROJECT_DIR` is taken as given). A project file with only global scope registered is an orphaned config: the row prescribes `/brewtools:<setup> purge project`, never `upgrade`.

An edited `semble-first.md` is never sent to plain `upgrade`: review the `diff -u`, or run `/brewcode:semble-setup upgrade --force` (backs up first, discards the edits). The skill never edits, merges or restamps that rule; an edit at the current stamp stays `current`.

</Spoiler>

<Spoiler id="task-tools" title="Task-tools offer and probe safety">

The highest settings layer that sets `CLAUDE_CODE_ENABLE_TODO_TOOLS` decides (local, project,
global); only `1`, `true`, `yes` or `on` turns it on. A higher layer's `"0"` reports
`off (<layer>)` with no offer. Otherwise the report asks once to add it to global or project
`settings.json`; `Leave off` changes nothing. The merge holds `settings.json.lock` and aborts
after 10 s if another setup holds it.

Probe fences run inline or through `scripts/fence-run.sh` (private 0700 temp directory, removed on exit).

</Spoiler>
