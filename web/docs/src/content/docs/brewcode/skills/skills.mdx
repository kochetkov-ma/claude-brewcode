# skills <Badge variant="secondary" text="opus" />

Manages the skill roster across global, project and plugin scopes. Give one free-form prompt; the skill picks a mode and tells you why. Status is the default, a list only on request.

## Quick reference

| Field | Value |
|-------|-------|
| Command | `/brewcode:skills` |
| Input | `[prompt] [status\|list\|create\|improve\|review\|sync]`; the mode word can appear anywhere |
| Specialist | `brewcode:skill-creator` agent |
| List source | `list-skills.sh`: global, project and every installed plugin |
| Description budget | Default ≤100 tokens (about 400 characters); spec cap 1024 characters |
| Model | opus |

## When to use

| Situation | Prompt |
|-----------|--------|
| See which skills exist and which are unhealthy | `/brewcode:skills` |
| Capture a workflow as a new skill | `/brewcode:skills create a skill that scans for hardcoded secrets` |
| Tighten activation or fix a broken skill | `/brewcode:skills improve ~/.claude/skills/` |
| Re-check skill files after the code moved | `/brewcode:skills sync session` |

## Modes

| Mode | Trigger | Source |
|------|---------|--------|
| status (default) | any "show me" / "status" / health intent | inline scan, no script |
| list | explicit "list" only | `list-skills.sh`, finds plugin skills in the dev checkout and the cache |
| create | "create" / "new" / "add" / "scaffold" | `brewcode:skill-creator` |
| improve | "improve" / "refactor" / "fix", or a bare name or path | `brewcode:skill-creator` |
| review | "review" / "validate" | one reviewer (project agent, else `general-purpose`): review, then double-check |
| sync | `sync`, `memory sync`, "bring in line with the code" | `references/mode-sync.md`: re-verifies each SKILL.md against the code, deletes first, never grows |

Batch is a flag: a plural form, "all" or several names fan out to parallel `skill-creator` spawns.

## Example

```bash
/brewcode:skills create a semantic code search skill
/brewcode:skills improve ~/.claude/skills/
```

The first researches and scaffolds a complete skill after one bundled question. The second processes every `SKILL.md` in the folder in parallel and reports the paths changed.

<Spoiler id="how-it-works" title="How it works">

<Steps>
  <li><div><strong>Input gate</strong><p>Reads the whole prompt. Empty input means status; an explicit mode anywhere wins.</p></div></li>
  <li><div><strong>Announce</strong><p>Prints one `PLAN`: INPUT, MODE with its reason, SCOPE, DO, RESULT. Write decisions go into one AskUserQuestion, at most four questions.</p></div></li>
  <li><div><strong>Menu</strong><p>Only on explicit request: Q1 picks the action, Q2 the variant; Other cancels.</p></div></li>
  <li><div><strong>Dispatch</strong><p>Routes to `list-skills.sh`, `skill-creator`, parallel spawns for batch, or `mode-sync.md` for sync.</p></div></li>
  <li><div><strong>Scoped sync</strong><p>After create or improve, the coordinator re-runs `mode-sync.md` on the written file only.</p></div></li>
  <li><div><strong>Report</strong><p>Prints mode, skills affected, findings, paths changed, and the next invocation if follow-up is warranted.</p></div></li>
</Steps>

</Spoiler>

Delegation of the fan-out follows the six-field brief in [Delegation](/brewcode/skills/#delegation). One subagent owns one skill directory.

Authoring a Claude Code mod is a separate job: see [mod-creator](/brewcode/agents/mod-creator/) and [mods](/mods/overview/).

## Technical details

<Spoiler id="invocation" title="Invocation and tool permissions">

| `disable-model-invocation` | `user-invocable` | Behavior |
|----------------------------|------------------|----------|
| false | true | User command and model invocation |
| true | true | User command only; policy for distributed skills (exceptions: `brewdoc:publish`, `brewtools:text-optimize`, `brewtools:text-human`) |
| false | false | Model invocation only; hidden from the command menu |
| true | false | Inaccessible; avoid |

Disabled model invocation also blocks subagent preloading. `allowed-tools` pre-approves listed calls for the invoking turn but is not an exclusive allowlist; `disallowed-tools` removes tools for that turn. Both clear on the next user message. Background execution can narrow tools further.

</Spoiler>

<Spoiler id="create-improve" title="Create / improve pipeline">

Reachable only via create and improve. Parameters come from the prompt, history or one bundled pre-write question:

| Parameter | Options | Notes |
|-----------|---------|-------|
| Invocation type | User-only / LLM-auto / Both | Sets `user-invocable` and matcher strategy |
| Testing depth | Quick / Standard / Deep | Scope of Phase 5 E2E |
| Review type | Simple / Quorum | Quorum for Standard and Deep only |

- **Phase 0 Discovery:** 2-3 parallel Explore agents scan skill patterns and project structure; create also researches the topic on the web.
- **Phase 4 Review:** Simple = one reviewer plus one verify agent. Quorum = three reviewers, 2/3 consensus, DoubleCheck, fixes verified findings.
- **Phase 5 E2E:** Deep only. Isolated temp project, `claude -p` execution, up to 2 retries per failed scenario.

Description: one line, what and when, 3-5 early trigger terms; combined description/`when_to_use` listing cap 1536 characters. These are house requirements, not an activation guarantee.

</Spoiler>

<Spoiler id="validate-skill" title="Validation: validate-skill.sh">

Every create/improve pass ends with `validate-skill.sh path/to/skill`. Checks 1-10 cover structure: YAML delimiters with the opening `---` on line 1, `name` as bare kebab-case (no leading, trailing or double hyphen) matching the directory, `description` caps (an unquoted description holding `: ` or ` #` only warns), body size, `EXECUTE` on bash blocks, Prompt Contract shape. The rest:

| Check | Severity | Catches |
|-------|----------|---------|
| 11 | warning | Unknown top-level frontmatter key |
| 12 | fail | A bare top-level `once:` (it belongs under a hook entry) |
| 13 | warning | `agent:` outside `Explore`, `Plan`, `general-purpose` |
| 14 | fail | A UTF-8 BOM at the start of `SKILL.md` |
| 15 | fail | A bare positional `$N` in the body (substituted at load) |
| 16 | fail | A plugin-root token other than the exact braced `CLAUDE_PLUGIN_ROOT` form |
| 17 | fail | `context:` with any value but `fork` |
| 18 | warning | `SKILL.md` over 500 lines |
| 19 | fail | `$ARGUMENTS` in a shell fence outside the canonical quoted heredoc |
| 20 | fail | `$ARGUMENTS` in prose outside the one canonical slot under `## Prompt contract` |
| 21 | fail | A `node -e "..."` program cut by a double quote or backtick |
| 22 | fail | A braced `CLAUDE_PROJECT_DIR` token meant as a literal (single quotes, quoted heredoc, JSON/JS/YAML fence) |
| 23 | warning | A braced `CLAUDE_*` token in prose with no `/` after it (incl. `${CLAUDE_EFFORT}`) is substituted at load: drop the dollar-brace when it names the variable |

The summary line reports `N passed, N failed, N warned`. Every managed skill follows the house prompt contract: prompt-first `argument-hint`, a `## Prompt contract` section, one five-label PLAN, and a multi-mode keyword table with `Mutates?` and a Russian keyword. Static validation proves structure, not activation: test user-only skills with `/name` and model-invocable ones with positive and negative prompts in fresh sessions.

</Spoiler>

<Spoiler id="sync-mode" title="Sync mode">

Runs `references/mode-sync.md` (steps S1-S6), shared with `/brewcode:agents sync`. Scopes `repo` (default), `session`, `commit`; verdicts STALE, DEAD, DUPLICATE, OBVIOUS, DRIFT, MISSING. Full scope and verdict tables: [agents sync mode](/brewcode/skills/agents/#sync-mode).

Announced as `Sync scope: <scope> — <evidence> | targets: <N> skills`. Non-growth: each file ends at or below its original line count, total delta ≤ 0; DELETE first, FIX, ADD last. A clean file reports `sync: no drift`.

</Spoiler>
