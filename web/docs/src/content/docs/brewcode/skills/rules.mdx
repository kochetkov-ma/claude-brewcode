# rules <Badge variant="secondary" text="sonnet" />

<Callout type="caution" title="Project scope only">Writes to project `.claude/rules/` only — never `~/.claude/rules/`.</Callout>

## Quick reference

| Field | Value |
|-------|-------|
| Command | `/brewcode:rules` |
| Input | free-form prompt, or empty |
| Model | sonnet |
| Specialist | bc-rules-organizer (Agent) |
| List source | `rules.sh list` (Bash) |
| Target dir | `.claude/rules/` (project only) |

## When to use

- After fixing a bug: capture what went wrong and the correct pattern
- After a code review: lock in the standards that were enforced
- After a session with many learnings: extract the 5 most impactful findings
- To inspect which rules already exist in the project
- To import structured knowledge from a `KNOWLEDGE.jsonl` file

## Examples

```bash
/brewcode:rules
/brewcode:rules what is the current state of our rules
/brewcode:rules capture what we learned fixing the auth bug
/brewcode:rules path/to/KNOWLEDGE.jsonl add new entries
/brewcode:rules list
```

## How it works

<Steps>
  <li><div><strong>Input gate</strong><p>Treats the whole of `$ARGUMENTS` as ONE free-form sentence — no keyword grammar, no argument parser. An empty prompt resolves to `status`; a non-empty one goes to mode selection; the menu appears only on an explicit request.</p></div></li>
  <li><div><strong>Auto-mode select</strong><p>Prints the <code>PLAN — brewcode:rules</code> block before the first action (<code>INPUT</code>, <code>MODE</code> with the reason, <code>SCOPE</code>, <code>DO</code>, <code>RESULT</code>). Defaults to <code>status</code> for any "show me" intent or when no keyword hits; detects <code>create</code>, <code>improve</code>, or <code>review</code> from explicit cues; <code>list</code> only on an explicit "list". Prompts work in English or Russian. A `.jsonl` path or inline prompt is treated as a knowledge source passed to the organizer, not a separate mode.</p></div></li>
  <li><div><strong>Menu (on request only)</strong><p>When the prompt explicitly asks for a menu, sends one AskUserQuestion with two questions. Q1 offers <strong>Status (rules)</strong> (recommended), <strong>Create new rules</strong>, <strong>Improve existing rules</strong> and <strong>Review rules</strong>. Q2 offers the variant: <strong>As chosen</strong> (recommended), <strong>Status (all: agents+rules+skills)</strong> or <strong>List (plain)</strong>. Cancel via Other stops the run.</p></div></li>
  <li><div><strong>Dispatch</strong><p>Routes <code>create</code> and <code>improve</code> to bc-rules-organizer via the Agent tool, passing the prepared knowledge block and mode; <code>review</code> goes to the project's reviewer agent, else <code>general-purpose</code>. For `list` mode, runs `rules.sh list` directly via Bash instead. After a write, a medium text-optimize pass runs on the written rule files when `brewtools:text-optimizer` is available; otherwise the skip is reported.</p></div></li>
  <li><div><strong>Real status</strong><p>For `status`, one Explore/Bash subagent collects and main assembles four blocks: <strong>Inventory</strong> (plugin / project / global counts, names, load path), <strong>State</strong> (enabled or disabled, legacy markers, model), <strong>Overlaps</strong> (same name across scopes, duplicate triggers) and <strong>Health</strong> (missing README or frontmatter, agents without a search tool, weak triggers, rules duplicated in CLAUDE.md). If bc-rules-organizer is unavailable, create and improve stop with: `brewcode:bc-rules-organizer not available — install brewcode plugin`.</p></div></li>
  <li><div><strong>Final output</strong><p>Prints a summary of rules added, merged, or skipped, grouped by target file. Skipped entries include the dedup reason (similarity %, cross-file antonym, or CLAUDE.md duplicate).</p></div></li>
</Steps>

## Modes

| Mode | Trigger | Execution |
|------|---------|-----------|
| `status` (default) | Empty prompt, no keyword hit, or any "show me" / "state" / health intent | One collector subagent gathers inventory, state, overlaps and health; main assembles the report |
| `list` | Explicit "list" only | Runs `rules.sh list` directly — no agent spawned, no status assembly |
| `create` | Conversational cue or menu selection | Creates missing rule files from plugin templates; accepts KNOWLEDGE.jsonl or inline prompt as knowledge source |
| `improve` | Conversational cue or menu selection | Rewrites weak or redundant entries for clarity; accepts KNOWLEDGE.jsonl or inline prompt as knowledge source |
| `review` | Conversational cue or menu selection | The project's reviewer agent (else `general-purpose`) reviews, double-checks findings and reports |
| batch | Plural, "all" or several names/paths | Not a separate mode: one specialist spawn per item, all fired in one message |

## Delegation

<Callout type="caution" title="Why the rule exists">
  A big task handed to one agent = an agent gone for an hour: you cannot observe it, cannot correct it, and it usually drifts off-target.
</Callout>

One subagent = **ONE bounded unit** — here, ONE rule file: roughly 5 files, roughly 10 steps. A batch is split into N tasks fired in **ONE message**, one `bc-rules-organizer` per target.

Every spawn prompt carries six fields. A bare one-line task is never enough:

| Field | Content |
|-------|---------|
| GOAL | the overall task and why it exists — the point beyond the file edit |
| ROLE | what this agent owns; what it must NOT touch |
| SCOPE | exact paths/commands in bounds + explicit out-of-bounds |
| CONTEXT | what is already done, by whom, what runs in parallel — trimmed to what THIS agent needs |
| CONSUMER | who or what uses the result next, and the shape it must fit |
| DONE | acceptance criteria + the exact report shape you want back |

For the organizer: ROLE is the target rule files only — never `CLAUDE.md`, never global rules. CONTEXT says the knowledge source is already chosen (do not re-ask) and the existing `.claude/rules/*.md` are the dedup baseline. CONSUMER is the sharpest constraint: Claude Code auto-loads `.claude/rules/*.md` into every session, so entries must be table rows, not prose.

<details>
<summary>Knowledge sources &amp; dedup</summary>

**Sources accepted:**

- `KNOWLEDGE.jsonl` path — parses each line; `t:"❌"` maps to avoid, `t:"✅"` maps to best-practice
- File path + inline prompt — organizer reads the file and uses the prompt as instruction
- Session learnings — the skill selects the 5 most impactful findings from the current conversation and formats them as ❌/✅ pairs

**Output files:** `avoid.md`, `best-practice.md`, `{prefix}-avoid.md`, `{prefix}-best-practice.md` — all inside `.claude/rules/`

**Validation:** `rules.sh validate` checks `avoid.md` and `best-practice.md` (both required) and `{prefix}-` files. `create` writes the two main files without `paths:`. A project that scopes a main file with `paths:` on purpose gets a `!` warning (the file then loads only when Claude touches a matching file), never an error. Keep the scoping or remove `paths:` to load the file at session start.

**3-Check dedup protocol:**

1. Within-file similarity: &gt;70% match → skip; 40–70% match → merge into existing entry
2. Cross-file antonym check: if the same pattern appears in both avoid and best-practice → keep the avoid entry only
3. CLAUDE.md duplicate: if the content already appears in `CLAUDE.md`, skip entirely. The string `"CLAUDE.md"` is forbidden as a Source value in rule entries

**Specialist:** bc-rules-organizer — acts as organizer only (no separate creator agent). Spawned via the Agent tool; the agent resolves paths via native `${CLAUDE_PLUGIN_ROOT}` (substituted in its .md at Agent spawn).

</details>
