# Skills

Skills (recipes) are slash commands that define *what* to do. Each skill is described in a `SKILL.md` file
with frontmatter metadata and instructions for agents. Brewcode includes 8 skills covering
the full task lifecycle -- from project analysis to E2E testing.

On top of those there is a **dynamic ninth skill**: it is not shipped with the plugin, it is **generated into every target project** by [`/brewcode:superreview`](/brewcode/skills/superreview/) and invoked there as `/superreview`, tailored to that project's tech stack, agents, rules and tracker. See the [emitted skill page](/brewcode/skills/review/) for details.

## Delegation — one contract, all eight skills

Every skill here fans work out to subagents, and all of them follow the same sizing rule.

<Callout type="caution" title="Why the rule exists">
  A big task handed to one agent = an agent gone for an hour: you cannot observe it, cannot correct it, and it usually drifts off-target.
</Callout>

One subagent = **ONE bounded unit**: one deliverable, roughly 5 files, roughly 10 steps. Anything bigger is split into N tasks and spawned in **ONE message**, in parallel. That is why `convention` runs 10 layer agents instead of one, `e2e` partitions scenarios across parallel agents, and `teams` creates agents one file per spawn.

Every spawn prompt carries six fields — a bare one-line task is never enough:

| Field | Content |
|-------|---------|
| GOAL | the overall task and why it exists — the point beyond the file edit |
| ROLE | what this agent owns; what it must NOT touch |
| SCOPE | exact paths/commands in bounds + explicit out-of-bounds |
| CONTEXT | what is already done, by whom, what runs in parallel — trimmed to what THIS agent needs |
| CONSUMER | who or what uses the result next, and the shape it must fit |
| DONE | acceptance criteria + the exact report shape you want back |

The same brief lives in the runtime templates these skills read — the `e2e` mode references, `convention`'s rules guide, `teams`'s roster template, and `superreview`'s emitted skill template — so a fan-out three levels deep still gets a full brief.

## Lifecycle

The recommended skill execution order for a standard project cycle:

<Steps>
  <li>
    <div>
      <strong>Superreview</strong>
      <p>Generate a per-project deep-review skill tailored to your tech stack and agents. <a href="/brewcode/skills/superreview/">superreview</a></p>
    </div>
  </li>
  <li>
    <div>
      <strong>Rules</strong>
      <p>Sync learned knowledge to project rules for future sessions. <a href="/brewcode/skills/rules/">rules</a></p>
    </div>
  </li>
  <li>
    <div>
      <strong>Teams (optional)</strong>
      <p>Create 5-20 project-specific agents with self-selection and performance tracking. <a href="/brewcode/skills/teams/">teams</a></p>
    </div>
  </li>
</Steps>

<Callout type="tip" title="Skill Management">
  Use <a href="/brewcode/skills/skills/">/brewcode:skills</a> to list, create, improve, or sync (delete-first, non-growth).
  The <a href="/brewcode/agents/skill-creator/">Skill Creator</a> agent handles the creation process.
</Callout>

## Skill dependencies

```
spec --> superreview --> /superreview (emitted into your repo)
  |
  +-- convention (optional)
  +-- rules
  +-- teams (optional)
```

<Callout type="note" title="Dynamic Teams — New">
  <code>/brewcode:teams</code> creates 5-20 project-specific agents with self-selection protocol,
  performance tracking, and automatic tuning. Run <code>/brewcode:teams</code> to build
  a team adapted to your project's domains and architecture.
</Callout>
