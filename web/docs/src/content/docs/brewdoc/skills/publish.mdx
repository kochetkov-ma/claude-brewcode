# publish

<Badge text="haiku" variant="secondary" /> <Badge text="model-invocable" variant="secondary" />

Prepare a local draft, publish supplied material, create and publish something new, or update an existing [BrewPage](https://brewpage.app) publication. You can publish anonymously or use an authorized BrewPage account. Anyone with an unlisted link can open it unless the publication has a reader password.

## Quick reference

| Field | Value |
|-------|-------|
| Command | `/brewdoc:publish [prompt] <text\|file_path\|directory_path\|zip_path>` |
| Options | `--ttl N` in days, `--entry filename` for sites, `--delivery-mode path\|subdomain` on create, `--state JSON` for Page data, `--domain hostname` for an eligible create |
| Invocation | Type the command or ask Claude in English or Russian. Claude can invoke the skill during a task. Headless and `dontAsk` runs need `Skill(brewdoc:publish *)` allowed |
| Result | A local draft, or the exact reader link and effective access from a confirmed publish or update |

## When to use

| Intent | Example request | Outcome |
|--------|-----------------|---------|
| Draft | “Prepare an RSVP draft for BrewPage, local only.” | Local HTML and its Page data declaration |
| Publish | “Share `report.md` as an unlisted link.” | Publishes the supplied material as-is |
| Compose and publish | “Create and publish a registration page that saves replies.” | Builds and publishes the requested page |
| Update | “Update this publication from `report.md`.” Supply the exact existing link | Replaces the requested content under its selected owner |

A direct invocation with supplied material defaults to publish. Ask for a draft or preview to keep the work local. The skill makes zero BrewPage calls or tool-discovery requests for a local draft. It needs no owner, visibility or domain setup.

## Example

```text
/brewdoc:publish Share report.md as an unlisted link without a password --ttl 30
```

Claude uses the requested access settings and asks about consequential choices only when unresolved. The result gives the exact reader link, effective access, and any applicable notice. For anonymous ownership, arrange protected key storage or private delivery before the first upload. An anonymous MCP call also needs a private tool result. See [how to choose a write route](#choose-one-write-route).

### Choose one write route

Use the BrewPage tools the host actually exposes. If it discovers tools on demand, discover once and verify the BrewPage binding, input schema and owner.

Before an MCP write that can return an owner key or a management link that grants access to its holder, verify an owner-only tool result or an authorized private handoff. An anonymous create can return both in tool text. Saving the key to a protected file leaves shared tool output visible. An established owner-only context is sufficient. If private delivery is unavailable, choose authorized REST with protected receipt handling before writing, or leave an MCP-only request pending.

Inline HTML can use the compact MCP tool with `publish({"content":"<h1>Report</h1>"})`. A representable static site uses the checked `files` list with each relative `path` and its `content`. A tool that imports a public URL needs a real reachable source URL. Local and sandbox paths go through local preflight.

Compact MCP preserves inline source by default. The REST runner sends explicit UTF-8 HTML with `verbatim=true` to keep the supplied markup. A pinned legacy tool may repair HTML. When exact source is required, select an authorized route that preserves it before sending a write.

Choose direct REST before a write when MCP is absent or lacks the required capability and the host permits REST with the selected owner proof. If the request requires MCP, wait for a compatible binding. A refusal stops the write. If a sent write times out, check the selected owner's receipt or inventory before considering another attempt. Never switch transports or owners to repeat a refused or already sent write.

### Choose the owner and access

- **Account.** Reuse the selected account when it is available and appropriate. For an explicit account-owned create, use a compatible tool with `requireAccount: true` and follow its first-party connection flow. The MCP client handles OAuth. If authorization is unavailable or declined, the account write stays pending. Signing into the website gives access to the website's account view. The selected tool still needs its own authorized connection.
- **Anonymous.** Reuse the selected saved owner when the route supports it. If several saved owners qualify, choose the exact saved publication for the intended owner. A fresh anonymous create uses neither a bearer credential nor a saved owner token. The REST runner supports `--anonymous` for this request. On MCP, `requireAccount: false` alone can still use a connected account.
- **Readers.** Link-only sharing uses an unlisted namespace. Choose `public` when eligible content should be discoverable in the gallery and sitemap. Password protection and owner unlisting hide a publication from discovery. JSON and other formats marked ineligible remain unlisted. Use the receipt's effective access when sharing. The REST runner takes an explicit password-file choice. For a password, provide an absolute path to a private local file. Use `''` for no password. Headless runs need any consequential choices already resolved.

<Spoiler id="technical-details" title="Formats, retention and hosting">

| Input | REST operation |
|-------|----------------|
| Plain text, Markdown or a UTF-8 `.md` or `.markdown` file | `POST /api/html?format=markdown` |
| A whole HTML document or a UTF-8 `.html` or `.htm` file | `POST /api/html?format=html` |
| Inline JSON object or array | `POST /api/json` |
| Other files, including non-UTF-8 HTML and Markdown files | `POST /api/files` with the original bytes |
| Built directory or site ZIP | `POST /api/sites` with a checked archive |

REST requests default to 15 days. BrewPage allows up to 30 days anonymously or up to 90 with a profile. Use the effective expiry from the receipt. An ordinary update keeps the original expiry.

Use `--delivery-mode path` to request a Promotion address with stricter script, cookie and embed limits, or `--delivery-mode subdomain` to request a dedicated origin. If omitted, the server chooses. Sites and non-public HTML-format pages require a dedicated origin. Page data can also require one. Keep the response's effective mode and link, including the trailing slash. A reused publication retains its own identity and expiry. Share password-protected reader links exactly as returned, without appending a password query.

</Spoiler>

<Spoiler id="flow" title="MCP and REST runner setup">

The skill can use the BrewPage MCP server already connected to Claude Code. For a client that starts a local stdio server, use the pinned package:

```bash
claude mcp add --transport stdio --scope project brewpage -- npx -y brewpage-mcp@3.0.0
```

The bundled runner handles local preflight and direct REST using narrowly scoped Bash access. Use macOS, Linux or WSL with Bash, curl, jq and Python 3 with `fcntl`. Git is used inside Git workspaces. Site checks also use Node.js and `unzip`, and packaging a directory uses `zip`.

Use `probe` to classify a local path and `limits` to read current service limits. Supply long text as a file or use `stage` and then `publish --run <id>`. Discard abandoned runs with `cleanup`. See the [bundled publishing recipe](https://github.com/kochetkov-ma/claude-brewcode/blob/main/brewdoc/skills/publish/references/publishing.md) for runner arguments.

</Spoiler>

<Spoiler id="security-and-history" title="Private receipts and owner history">

- Share the exact returned reader link and effective access. A management link is a private way to manage that item. An owner key may manage multiple publications and create more under the same owner. Keep both out of shared output, content, logs and command arguments.
- An account-owned result is in the verified account's publications. An eligible anonymous create can issue a new key. Arrange owner-only delivery or an authorized private store first. The Claude runner's workspace store is `.claude/brewpage-history.md` with mode `0600`. The runner also accepts proof from an absolute owner-only file with `--owner-token-file`. The `owner-store` operation imports and reads back an authorized key locally.
- The ordinary runner receipt shows reader-facing details and storage status. It omits keys, private management URLs and credential storage paths. Use `--private-output` only after verifying an owner-only output channel. If the owner declines saving, `--no-save` requires `--private-output`.
- If a publication succeeds and history saving fails, report both. In a verified owner-only channel, use the runner's `owner-recovery --private-output` to read the workspace's protected fallback receipt locally. After restoring protected history storage, import that receipt with `owner-store`. It clears the matching fallback only after verified readback. A save failure is never a reason to create the publication again. If a reused result grants no owner access, share the reader link and say management access is unavailable.

See the [ownership and receipts recipe](https://github.com/kochetkov-ma/claude-brewcode/blob/main/brewdoc/skills/publish/references/ownership.md).

</Spoiler>

<Spoiler id="owner-operations" title="Update and manage an existing publication">

Use `update_publication` with the exact kind, namespace and ID from a private receipt or authorized inventory. The REST runner accepts the exact saved reader link or recorded owner API URL. A reader link identifies the item when it matches a saved receipt. Owner authorization comes from the account or private proof. For example, update a rendered Markdown report using saved proof:

```bash
bash ${CLAUDE_SKILL_DIR}/scripts/brewpage-run.sh update html --target '{saved_url}' --password-file '' --path '/absolute/path/report.md'
```

On a content replacement, the empty password-file slot keeps the existing password. Omit `state` for a content-only edit to keep its Page data settings and entries. A missing, rejected or read-only target requires a separate request before any fresh publish.

A site replacement sends the complete desired file set. To keep the existing entry, omit `--entry` with the REST runner. It verifies the existing entry from owner-authorized metadata and keeps it. With MCP, send that verified path explicitly as `entry`. If the path is unresolved or missing from the replacement, leave the update pending until the entry is resolved.

For settings or deletion, use the authorized private management view or the corresponding tool if the host exposes it. A hosting change uses the current hosting version and can return a different reader link. Check that result before sharing.

</Spoiler>

<Spoiler id="site-bundles" title="Site bundles and preflight">

Publish a build directory or ZIP with an HTML entry and all required assets. Use `--entry` for a specific relative path. On create, the default prefers a root `index.html` when present, then a verified entry from the archive.

```bash
bash ${CLAUDE_SKILL_DIR}/scripts/brewpage-run.sh preflight site-dir --path '/absolute/path/dist' --entry 'index.html'
```

Pass the real password and owner-token file paths when used, along with repeatable `--exclude-file` for other protected files. Directory checks exclude protected inputs and keep allowed web assets, including the root `.well-known/`. A directly selected protected file or a ZIP containing a reserved credential input fails before any write. Confirmation cannot override the refusal. Rebuild the bundle without those entries.

For other flagged ZIP entries, `CONFIRM` presents the manifest and `REVIEW_SHA256` before upload. Recheck with `--confirmed --review-sha256` and the displayed digest after approval. Changed bytes require a fresh manifest and approval. Use the private snapshot from local preflight or its checked MCP file list. Clean up the preflight run after use or cancellation.

Read current server limits before a large upload. The runner exposes the same read-only request with `limits`.

```bash
curl -fsS -A "ClaudeCode/6.13.4 (+https://brewpage.app)" https://brewpage.app/api/limits
```

</Spoiler>

## Page data

For an RSVP, load the classic `https://brewpage.app/js/state.js` before calling `bp.state()`. Guard the call and show a visible message if saving is unavailable. Add a visitor notice and a private collection. Include the declaration with the page on publish, using MCP's `state` or the REST runner's `--state`.

```json
{"collections":{"rsvps":{"mode":"private","maxDocsPerVisitor":1}}}
```

A draft returns the HTML and declaration together. A localhost preview can store answers in the browser. After publishing an owned test page, submit a reply, reload and verify it in the private Data tab. For a shared guestbook, use a shared collection only when requested and display entries as text. For newly authored pages, reserve image space, load the initial view eagerly, and apply `loading="lazy"` to images and iframes below the fold. See the [offline RSVP recipe](https://github.com/kochetkov-ma/claude-brewcode/blob/main/brewdoc/skills/publish/references/page-data.md).

## Custom domains

An eligible HTML page or site without a reader password can use a hostname you control. Resolve the selected account or eligible owner proof before publishing with a requested domain. For a new publication, use `domain` on compatible MCP or `--domain hostname` with the REST runner and eligible account owner proof. For an existing item, use the supported attachment operation for that exact publication. See the [custom domain recipe](https://github.com/kochetkov-ma/claude-brewcode/blob/main/brewdoc/skills/publish/references/custom-domain.md).

Apply the exact DNS records from the response, request one check after changing DNS, then read status on the returned schedule. The BrewPage link is the working address while DNS is pending or verification is in progress. Report the custom URL as live when the response confirms `active` and `serving: true`. A failed attachment after a confirmed create leaves the original publication available.
