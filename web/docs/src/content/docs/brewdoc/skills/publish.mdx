# publish — share content, get link

<Callout type="caution">
**Choose visibility before publishing.** The skill resolves the namespace and password policy before upload. Owner tokens needed for deletion are stored locally and never printed to conversation.
</Callout>

## Quick reference

| Field | Value |
|-------|-------|
| Command | `/brewdoc:publish [prompt] <text\|file_path\|directory_path\|zip_path> [--ttl N] [--entry filename] [--delivery-mode path\|subdomain]` |
| Arguments | Inline text, a file path, a directory, or a `.zip` archive; prose naming a path resolves against the current directory |
| Options | `--ttl N` = days (default 15); `--entry filename` = site entry; optional `--delivery-mode path\|subdomain` = creation mode |
| Model | haiku |
| Invocation | model-invocable (`disable-model-invocation: false`): type `/brewdoc:publish` or ask Claude ("publish this", "share a link") |
| Tools | `Read, Bash(bash ${CLAUDE_SKILL_DIR}/scripts/brewpage-run.sh *), AskUserQuestion, Glob` |
| Permissions | No Bash or Write prompts: every step is one `brewpage-run.sh` command that matches the skill's single allowed-tools rule. When Claude starts the skill itself, Claude Code asks once for the `Skill` call in default mode; headless and `dontAsk` runs need the allow rule `Skill(brewdoc:publish *)` in settings |
| Requires | `jq` and `curl` on `PATH`; `zip`/`unzip`/`node` as well for directory or zip site uploads |

## When to use

- **Share a report instantly** — `/brewdoc:publish report.md` → shareable link
- **Host a JSON dataset** — `/brewdoc:publish '{"status":"ok","count":42}'` → browseable JSON page
- **Upload any file** — `/brewdoc:publish screenshot.png --ttl 1` → direct download link, expires in 1 day
- **Deploy a static site** — `/brewdoc:publish ./dist/ --entry index.html` → full multi-file site with routing
- **Ask mid-task in plain language** — after Claude generates a report, say "publish the report and give me the link"; Claude can start the skill itself; you still answer the namespace and password questions (headless runs use the defaults: suggested name, no password), then it returns the URL
- **Password-protect a page** — choose an existing local password file without exposing its contents in chat
- **Host public content on its own address** — use `--delivery-mode subdomain` and choose `public` at the namespace prompt

## Examples

```bash
# Publish inline text or markdown
/brewdoc:publish "Hello, world!"
/brewdoc:publish report.md

# Choose public at the namespace prompt for either public hosting mode
/brewdoc:publish report.md --delivery-mode path
/brewdoc:publish report.md --delivery-mode subdomain
```

```bash
# Publish a JSON literal
/brewdoc:publish '{"status": "ok", "count": 42}'

# Publish a file (any MIME type)
/brewdoc:publish screenshot.png --ttl 1
```

```bash
# Deploy a multi-file site from a directory
/brewdoc:publish ./dist/ --entry index.html

# Upload a pre-zipped site archive
/brewdoc:publish site.zip --ttl 14
```

## Visibility and indexing

**brewpage.app** is free instant hosting: HTML pages, JSON documents, files, and multi-file sites. Default TTL is 15 days; override with `--ttl N`. For the public gallery, visit [brewpage.app](https://brewpage.app).

Private means unlisted, not access-restricted: anyone with the link can open it unless a password is set. Eligible, unprotected HTML pages, sites and files in `public` can be listed in the gallery
and indexed, including on native subdomain hosts. Non-public, password-protected and
ineligible publications use `noindex`. Eligibility does not guarantee indexing or search ranking.
Choose the namespace before uploading; this does not change the skill's hosting defaults.

## Modes

| Input | Detected type | Endpoint |
|-------|--------------|----------|
| Plain text or markdown string | HTML | `POST /api/html?format=markdown` |
| Existing .md or .markdown file | MARKDOWN | `POST /api/html` with markdown format; rendered page rather than raw download |
| Starts with `{` or `[` | JSON | `POST /api/json` |
| Existing local file path | FILE | `POST /api/files` (multipart) |
| Directory or `.zip` file | SITE | `POST /api/sites` (archive built/verified by `publish.mjs`, then uploaded) |

SITE is checked first — directories and `.zip` files would otherwise match the FILE branch.

Entry file detection for sites: `--entry` flag → `index.html` if present → first `.html` alphabetically.

## Hosting modes

`--delivery-mode` accepts only `path` or `subdomain`. When omitted, the skill sends no
`X-Delivery-Mode` header and lets the server choose. The header stays outside the authored
text, JSON and multipart fields. The modes apply to publications with the server's `new-v1` routing
metadata and depend on the server rollout; existing publications retain their current links and behavior.

| Fresh publication with `new-v1` metadata | Default | Explicit choice |
|-------|-------|-------|
| Public HTML/Markdown, JSON or file | Promotion (`path`) | `path` or `subdomain`, including with a password |
| Site in any namespace | Dedicated subdomain (`subdomain`) | `subdomain`; `path` is rejected |
| Non-site outside `public` | Dedicated subdomain (`subdomain`) | `subdomain`; `path` is rejected |

**Promotion** uses a `brewpage.app` address for branded sharing. Eligible public content can
be discoverable; HTML has stricter script, cookie, embed and navigation restrictions.
**Dedicated subdomain** gives the publication its own origin with fewer presentation
restrictions. Choose it if Promotion prevents your HTML from working as intended.

Neither mode guarantees search ranking or third-party widget compatibility. A namespace name
may appear in the publication address and DNS/TLS metadata. Subdomains
separate DOM and storage, but shared parent-domain cookie interference remains possible.
Protected Promotion also retains the access risks of existing executable apex content.
Passwords or revocation cannot recall downloaded or offline-cached copies.

The response decides the effective mode. A new upload request can also return an existing publication. If the server reuses a publication, keep that
publication's identity, cohort, mode and exact URL even when they differ from the requested
mode. Missing or null legacy routing metadata means **Existing link**; do not infer a mode
from its hostname. **Always use the server's returned link, shared exactly, including its trailing slash.**

New password-protected links remain clean: do not append `?p=`. Browser readers unlock on
the trusted `unlock.brewpage.app` gateway; programmatic password requests still use
`X-Password` on the apex API. Existing password-link behavior remains unchanged.

## Flow

<Steps>
  <li>
    <div>
      <strong>Parse arguments</strong>
      <p>Extracts <code>--ttl N</code> (default: 15 days), <code>--entry filename</code> and optional <code>--delivery-mode path|subdomain</code>. Resolves a path named in prose; asks what to publish if neither a path nor content can be resolved.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Detect content type</strong>
      <p>For a path, runs <code>brewpage-run.sh probe</code> (read-only) to get the type, absolute path and size. Classifies the input as SITE, MARKDOWN, FILE, JSON, or HTML — in that order — and shows a pre-publish summary.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Ask namespace</strong>
      <p>Offers <code>public</code> for eligible gallery/search discovery, a suggested meaningful unlisted slug, or a custom value (1–32 lowercase letters, digits or hyphens). Namespace sets visibility and helps determine hosting defaults; the response supplies the actual address.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Resolve password policy</strong>
      <p>Choose no password or provide the absolute path to an existing local password file with at least four characters. The prompt asks for the path only. Password contents stay outside chat and model-visible tool output; private transport supplies the upload header.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Publish</strong>
      <p>Runs one <code>brewpage-run.sh publish</code> command with the namespace, TTL, optional entry file, optional <code>--delivery-mode</code> and <code>--password-file</code> flags. When the full command would pass 8,000 characters, the text or JSON is staged first: <code>stage</code> calls pass the content in chunks of up to 6,000 characters, then <code>publish --run</code> joins them. The script validates every value, builds and verifies site archives, adds <code>X-Delivery-Mode</code> only when requested, and saves the owner token, exact link, owner API and identity metadata in project-root <code>.claude/brewpage-history.md</code> without printing the token.</p>
    </div>
  </li>
  <li>
    <div>
      <strong>Return result</strong>
      <p>The script prints one decisive line. <code>OK &lt;url&gt;</code> (sites add <code>| Files: N</code>) returns the exact server URL. <code>CONFIRM: ...</code> (exit 2, nothing uploaded) means a supplied ZIP has flagged entries: after you confirm, the same command reruns with <code>--confirmed</code>. <code>FAILED: ...</code> reports the safe failure line and withholds the response body, which may contain an owner token. The script removes its private run directory on every exit.</p>
    </div>
  </li>
</Steps>

<details>
<summary>Internals</summary>

**Security — owner token:** The `ownerToken` field from the API response is captured inside the script and written directly to `.claude/brewpage-history.md`. The LLM only sees `OK {url}`, `CONFIRM: ...` or `FAILED: ...` — never the token value, and never the raw response body on failure.

**Security — password policy:** each upload uses explicit none or file mode. None ignores all
password files, including stale inputs from previous runs. File mode takes only an existing
local source path; the helper copies its bytes into private transport and supplies a curl header
file. Passwords never become shell literals, curl arguments, conversation output, or generated
random values. Invalid files or control characters stop publishing.

**One script, one rule:** every shell step is `bash ${CLAUDE_SKILL_DIR}/scripts/brewpage-run.sh <probe|stage|publish|cleanup> ...` with single-quoted values. The skill's single `Bash(...)` allowed-tools rule matches that exact shape, so nothing prompts, headless included. Any other shape (quoted script path, `cd` prefix, `&&` chain, `$(...)`) falls back to the normal permission prompt, and commands over 8,000 characters are always refused, hence `stage`.

**Run isolation:** the script allocates a unique private run directory (`brewpage.XXXXXX`, mode 700) under
`$TMPDIR`, else `/tmp`, outside `.claude/`, so no protected-path prompt appears. Only the script creates, fills and removes it, so the skill needs no `Write` grant. Runs never share a directory; `cleanup --run` removes a staged but unpublished run. Only the password source path is recorded, and its contents are not read through model-visible tools.

**History file format:** the helper resolves the project root from `CLAUDE_PROJECT_DIR`, Git,
an upward `.git`/`.claude` search (a `.claude` in `$HOME` or in the directory whose `.claude` IS `$CLAUDE_CONFIG_DIR` is a profile, not a project marker, and is skipped; a `.git` there still counts), or the current directory. It creates
`<project-root>/.claude/brewpage-history.md` with mode `600` and git-ignore protection, then
appends the exact URL, token, TTL, type, returned `ownerLink` and identity metadata. Existing
history rows remain unchanged.

```markdown
| Date | URL | Owner Token | TTL | Type | Owner API | Identity |
|------|-----|-------------|-----|------|-----------|----------|
```

**Delete a published page:**

Use the returned `ownerLink` stored as **Owner API**, not the viewer's subdomain. In the
examples below, `OWNER_API` is that apex API URL and `TOKEN` stands for the locally stored
owner token. Existing rows without metadata keep their existing API identifiers; never
derive a namespace or resource ID by splitting a hostname.

```bash
curl -s -X DELETE "$OWNER_API" \
  -H "X-Owner-Token: TOKEN"
```

**Update a published site (keep the same URL):**

```bash
curl -s -X PUT "$OWNER_API" \
  -H "X-Owner-Token: TOKEN" \
  -F "archive=@/absolute/path/to/new-bundle.zip"
```

For a site, `OWNER_API` is its returned apex `/api/sites/{ns}/{id}` URL. The bundle fully
replaces the file set and retains the host. Ordinary PUT/settings updates preserve the
mode; do not send `X-Delivery-Mode` to change it.

**Change hosting after publication:** only NEW public non-sites may change modes. Use
stored identity metadata for the API segment (`html`, `files`, `json`, `kv`), namespace
and ID. Owner-only `GET /api/{type}/{ns}/{id}/hosting` reads the current projection and
version; `PATCH` that apex endpoint with `X-Owner-Token` and JSON:

```json
{"deliveryMode":"subdomain","expectedVersion":1}
```

Use the version returned by GET, not a guessed value. A successful change increments
`hostingVersion`; requesting the current mode with the current version leaves it unchanged.
The assigned host is retained through both directions of a change, and issued URLs become
safe redirects. Use the returned link and version afterward.

| Response | Meaning |
|-------|-------|
| `403` | Owner authorization failed |
| `400` | Invalid mode/version or `HOSTING_MODE_LOCKED` for OLD or a forced-mode identity; sites have no PATCH endpoint |
| `409 HOSTING_VERSION_CONFLICT` | Reload current settings before retrying |
| `503` | Hosting changes temporarily unavailable; fresh creation can also fail with `HOST_ALLOCATION_FAILED` |

**Namespace rules:** lowercase letters, digits and hyphens, 1–32 characters. Suggested names
are lowercase and content-derived (`api-docs`, `report-q2`), never random or truncated.

**Site uploads:** directory → `scripts/publish.mjs pack --dir <dir> --out <archive.zip>` builds the archive, removing any stale target first (a pre-created 0-byte file would make `zip` exit 3), then checks `zip`'s exit status, verifies the result with `unzip -t`, and requires a non-zero size — any failure deletes the archive and exits without touching `curl`. The archive is POSTed as `archive=@$TMPZIP` and the temp file removed after. `User-Agent: ClaudeCode/1.0` header included.

**Archive contents — allowlist, not denylist:** only known web-asset extensions (`.html .css .js .json .svg .png .woff2 .pdf .md` …) are packed; dotfiles, `.env`, `.git/`, `node_modules/` and symlinks are dropped before `zip` ever runs. A supplied `.zip` is inspected rather than rewritten — an entry matching a sensitive pattern (`.env`, `id_rsa`, `secret`, `credential`, `password`, `token`, `.pem`/`.key`/`.p12`/`.crt`/`.map`) blocks the upload until you confirm.

**Tests:** `bash brewdoc/skills/publish/tests/run.sh` — archive, helper and prompt checks;
no network or real upload. Local tests do not prove server rollout or browser rendering.
