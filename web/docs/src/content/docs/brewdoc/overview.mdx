# Brewdoc Overview

Brewdoc keeps documentation in sync with the codebase, documents your Claude Code setup, and exports documents to PDF or a shareable link. 5 skills, no agents, no registered hooks; `docsync-setup` installs optional hooks into your project on request.

## Install

<InstallPrompt plugin="brewdoc" mode="install" />

## What you get

| Skill | Does | Link |
|-------|------|------|
| `docsync-setup` | Tracks doc staleness by frontmatter date through project hooks | [Skill](/brewdoc/skills/docsync-setup/) |
| `my-claude` | Documents your Claude Code installation, architecture or a research query | [Skill](/brewdoc/skills/my-claude/) |
| `memory-sync-setup` | Generates a project-local `/memory-sync` skill | [Skill](/brewdoc/skills/memory-sync-setup/) |
| `md-to-pdf` | Converts Markdown to PDF with reportlab or weasyprint | [Skill](/brewdoc/skills/md-to-pdf/) |
| `publish` | Publishes text, files or sites to brewpage.app, returns the URL | [Skill](/brewdoc/skills/publish/) |

Commands, arguments and models: [Skills](/brewdoc/skills/).

```bash
/brewdoc:docsync-setup sync           # Sync stale docs (with confirmation)
/brewdoc:md-to-pdf README.md          # Convert markdown to PDF
/brewdoc:publish "Hello world"        # Publish to brewpage.app, returns the URL
```

## How it fits

Each skill is self-contained and independent of the others; the shared `-setup` convention gives the two setup skills one mode set. Brewdoc covers documentation utilities; [Brewcode](/brewcode/overview/) is the authoring toolkit: skills, agents, rules, semantic search, conventions and E2E tests. Both install from the same `claude-brewcode` marketplace.

## Technical details

<Spoiler id="naming" title="Naming and invocation rules">

A `-setup` suffix marks a skill that **installs a mechanism you afterwards use instead of the skill**: project-local hooks, or a generated `/memory-sync` command. Recurring tools keep bare names (`md-to-pdf`, `publish`, `my-claude`). Every `-setup` skill shares one mode set, in this order: `status | install | upgrade | enable | disable | uninstall | purge`; no argument means `status` when installed, `install` when not. Every brewdoc skill except `/brewdoc:publish` is user-invoked only (`user-invocable: true` + `disable-model-invocation: true`); `publish` is model-invocable, see the [FAQ](/faq/#auto-invoke).

</Spoiler>

<Spoiler id="plugin-structure" title="Plugin structure">

```
brewdoc/
├── .claude-plugin/plugin.json   # manifest
├── hooks/hooks.json             # {"hooks":{}} -- no hooks registered
└── skills/                      # docsync-setup, my-claude, memory-sync-setup (references/), md-to-pdf, publish
```

`docsync-setup` installs project-local hooks into the *target* project, not into brewdoc. Skills use `${CLAUDE_SKILL_DIR}` for their own files.

</Spoiler>

<Spoiler id="behaviour-notes" title="Safety and scope behaviour">

Docsync installation validates inputs before writing hooks, configuration and settings, retains settings backups and session state, and on a write failure restores only files that still match this run's writes. A generated memory-sync follows restrictions such as "only rules" or "do not touch agents". Scope, depth and reach are separate choices. Claims are checked against current code, no file ends longer than it started, and a checker other than the writer verifies each batch.

</Spoiler>

<Spoiler id="artifact-metadata" title="Artifact metadata">

Every artifact a brewdoc `-setup` skill installs carries the shared provenance fields, resolved from the plugin's `.claude-plugin/plugin.json`. Field table: [Brewcode overview](/brewcode/overview/#artifact-metadata). `/brewcode:setup-status` reads them back and reports older installs as stale.

</Spoiler>
